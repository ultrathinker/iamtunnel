# THREATS.md — iamtunnel threat model and security analysis

This document is built on the design in `SPEC.md`, the wire protocol in
`PROTOCOL.md`, and the project's own audit history, with lessons carried over
from the predecessor prototype. It reflects the SPEC 0.3 / Protocol v1
architecture: starting the server no longer opens the door or writes an
authorized-keys entry (the door is closed by default and opened only by the
gateway, on a person's confirmed request, over the persistent
`iamtunnel-control` channel); the watchdog starts strictly BEFORE the key
line is written; the server enforces its own independent deadline ceilings
(`maxDoorIdle`, `maxDoorHard`); and the earlier architectural dead end around
reopening the door, and the fictitious `osUser` privilege check, are both
closed. It covers the assets defended, the attacker models considered, a
detailed walk-through of compromise scenarios, the door's layered invariants,
a failure-window matrix, accepted risks, the status of previously found
design defects, hardening opportunities, and an honest comparison of what the
current architecture improved and what it made worse.

```iamtunnel-runbook-events-v1
{"written":["admin.op","auth.failure","auth.handshake_failure","auth.success","door.close","door.open","door.sanitize","enrol.failed","hostkey.mismatch","risk.approval","session.drop","session.risk"],"notWrittenThisBuild":[]}
```

## 1. What we defend (system assets)

1. **People's private keys** — SSH private keys (Ed25519 / RSA ≥ 3072),
   belonging to users (`~/.ssh/id_ed25519`, `%LOCALAPPDATA%\iamtunnel\key`, or
   in `ssh-agent`). These establish a person's identity.
2. **Machine enrollment key** — a machine's unique private key (Ed25519),
   generated during Set-up (SPEC §3.4) and kept on the machine. Used for
   mutual authentication with the gateway and to build the persistent SSH
   transport carrying the control channel.
3. **Door key pair** — an ephemeral Ed25519 pair generated by the gateway
   (SPEC §5.2, PROTOCOL §5.1) only on a confirmed person reservation, and
   handed to the machine's server over `iamtunnel-control` via `door.open`.
   The private half lives only in the gateway process's memory while the
   door is in `opening`, `open` or `closing`, and is never written to disk on
   either side; the public half is written by the machine to
   `administrators_authorized_keys` only after the ed25519 key is validated,
   local deadline ceilings are checked, and the watchdog has already
   started.
4. **Host keys**:
   - *Gateway host key* (`/var/lib/iamtunnel/hostkey`) — proves the
     bastion's identity to clients and machines, and defends against
     man-in-the-middle.
   - *Target machine's host key* (`sshdHostKey`) — the local OpenSSH host
     key, captured and verified by the gateway at registration step 3 (SPEC
     §3.4, PROTOCOL §7), with a control SSH public-key auth check of
     `requestedOsUser` through a temporary door, no shell/exec, and pinned in
     `state.json` (`hostKeyStatus: match` on agreement, `mismatch` on a
     divergence, which blocks the door).
5. **Grants and deadlines** — `state.json` records (SPEC §4.3) of the tuple
   `grant{person, machine, until, caps}`, enforcing least privilege and
   time-boxed access.
6. **Session recordings** — files under the gateway's
   `/var/lib/iamtunnel/recordings/`: timed asciicast (`.cast`), a scrubbed
   text transcript (`.txt`), metadata (`.meta`) for interactive sessions and
   PTY exec, and a streamed `.exec.jsonl` for non-interactive exec. These are
   the legally significant evidence of what an operator did on the server
   (§6.5).
7. **Event journal** — the append-only `/var/lib/iamtunnel/events.jsonl`,
   recording every authorization fact, admin action, door open/close, and
   host-key mismatch (§3.5).
8. **Target OS access** — a shell session (PowerShell / cmd.exe, or the
   Linux/macOS equivalent) under the local administrator account
   `verifiedOsUser` (§4.3).
9. **One-time first-contact secrets** — the first-admin bootstrap token
   (§3.3, 24h, one attempt), the pairing PIN for a new admin (§3.3, **2
   minutes**, an address ban after three misses and the window itself
   burning after ten misses across all addresses, IPv6 counted by /64), and
   one-time machine invitations (`iamtunnel-enrol://...`, §3.4, **15
   minutes** since 1.3; was 24 hours). Compromising any of these can hijack
   an admin or machine identity. Since 1.3 each travels as **one string**
   carrying the address, its fingerprint, and the secret itself (§3.6): a
   captured string is now self-sufficient, and its value is held down not by
   channel separation but by short life, one-time use, and an attempt
   limiter. The accepted residual risk is stated plainly in §6, item 6.

## 2. Who attacks (attacker models)

Seven categories of attacker are considered, with different starting
privileges, network position and goals:

1. **An external attacker on the Internet** — no valid credentials or keys;
   network access only to the gateway's public port (default TCP 2222).
   Goals: bypassing SSH auth, guessing keys under the raised
   `MaxAuthTries=32`, exploiting a vulnerability in
   `golang.org/x/crypto/ssh`, denial of service.
2. **A person with valid, expired, or revoked access** — a legitimate user
   (former employee, contractor) whose key is still in `state.json`, but
   whose grant's `until` has passed or was revoked. Goal: unauthorized entry
   despite the time policy, or riding on a background process left running
   from an earlier session.
3. **A person with valid access to machine A wanting machine B** — an
   authorized user with an active grant for A but not B. Goal: lateral
   movement through the gateway, spoofing the target machine identifier,
   riding someone else's tunnel.
4. **A machine's local administrator** — a privileged user on the managed
   host, with access to other users' sessions, the `sshd` service, the
   `iamtunnel.exe` process and the authorized-keys file. Goals: forging
   session records, hiding activity from the gateway, persistence after the
   tunnel closes.
5. **A compromised gateway account** — an attacker with access to the
   gateway's OS, as the `iamtunnel` user or root. Has access to
   `/var/lib/iamtunnel/`, the gateway daemon's memory, and the network
   interface. Goals: intercepting interactive sessions in plaintext,
   extracting door private keys from memory, opening doors over
   `iamtunnel-control` without authorization, modifying `state.json`, forging
   `events.jsonl`/`.cast` entries.
6. **An on-path network attacker (MITM)** — controls network segments
   between client and gateway, or between gateway and machine (ISPs,
   compromised routers, ARP/BGP spoofing). Goals: passive metadata capture,
   host-key spoofing, command injection, denial of service via keepalive
   disruption or malformed control-channel injection.
7. **Malware on a client workstation** — a process (privileged or not) on an
   operator's machine, with access to `%LOCALAPPDATA%\iamtunnel\key`
   (stored without a passphrase per §3.1), the `ssh-agent` socket, and the
   terminal emulator process. Goals: stealing the client's private key,
   injecting commands into the operator's active terminal, intercepting
   session output.

## 3. Compromise walk-throughs by attacker model

Following SPEC §6.6, every compromise scenario and attacker class is walked
through below.

### 3.1. Compromise of an administrator's key

- **What the attacker gets immediately**:
  - Full administrative access over SSH (`iamtunnel admin ...`, the JSON
    exec channel, SPEC §3.3, §5.3).
  - The ability to issue arbitrary grants (`admin grants grant`) to any
    person on any registered machine, for any duration.
  - The ability to generate machine invitations
    (`admin machines enrol-code <name>`; a name is required since 1.4).
  - Forcibly ending existing sessions (`admin sessions kill`) and revoking
    active grants (`admin grants revoke`).
  - Fetching every archived session recording (`admin recordings fetch`).
  - Changing a machine's target Windows user (`admin machines set-user`).
  - Rotating the gateway's host key (`admin gateway rotate-hostkey`).
- **What the attacker cannot get, and why**:
  - The attacker **cannot** reach a powered-off or disconnected target
    machine: per §3.2 and §5.2 the machine sits behind NAT and dials out
    itself; the gateway can't open a connection to an absent node.
  - The attacker **cannot** bypass session recording: per principle 3 and
    §5.1, the gateway unconditionally terminates the session and centrally
    records `.cast` and `.txt` (or lossless `.exec.jsonl`); the admin
    protocol has no command to turn recording off.
  - The attacker **cannot** connect to a target machine without presenting a
    person's private key whose name (`person`) matches the registered grant
    (§6.1).
  - The attacker **cannot** open a door on the target machine directly
    through the admin exec interface: `door.open`, `door.close`,
    `door.status`, `door.sanitize` are not exec commands at all (SPEC §5.3,
    PROTOCOL §6), and calling them via exec is refused as unknown — the
    dictionary also defines `E_CONTROL_ONLY`, but this build's answer on this
    path is the plain "unknown command" text, a documented wording gap. The
    door is opened by the gateway only through the internal
    `iamtunnel-control` channel, gated on an existing `grant{person, machine,
    until}` and the person's own successful authentication with the key
    paired to the person's registered one.
- **Detection in the event journal (`events.jsonl`)**:
  - `admin.op` entries appear for admin calls, with the operation in
    `result` (§3.5).
  - `auth.success` events for the admin's key from unusual source addresses.
  - Sessions opened to critical hosts at unusual hours.
- **Recovery procedure (given a documented design gap)**:
  1. The hosting operator connects to the Linux VPS directly (out-of-band
     console).
  2. Stop the gateway immediately: `systemctl stop iamtunnel-gateway`
     (graceful drain per SPEC §3.5), or `kill -9` the gateway process for an
     instant cut of the attacker's active connections. There is no
     `iamtunnel gateway stop` console command.
  3. If a **second trusted admin** is registered: start the gateway, and from
     the second admin revoke the compromised key:
     `iamtunnel admin people keys remove <admin-person> <fingerprint>`
     (§3.3).
  4. If the **only** admin key is compromised: there is no built-in local
     command to add one on a running gateway from scratch outside the
     pairing path — see `docs/RUNBOOK.md` §5.11 for the supported recovery
     (`gateway pair` on a stopped gateway).
  5. Audit `events.jsonl` and `state.json` for unauthorized people, keys or
     grants added; revoke anything suspicious.

### 3.2. Compromise of the gateway's disk (stolen backup / physical access)

- **What the attacker gets immediately**:
  - The `state.json` file: people and their public keys, the machine list,
    machine public keys (`machineKey`), pinned target OpenSSH host keys
    (`sshdHostKey`), assigned `osUser` values, the grant history (§4.3).
  - The gateway's private host key (`/var/lib/iamtunnel/hostkey`): enough to
    stand up a fake clone gateway on another IP and intercept connections.
  - The full recordings archive (`/var/lib/iamtunnel/recordings/`): every
    historical `.cast`, `.txt`, `.exec.jsonl` and `.meta` file, which may
    hold sensitive data, passwords and tokens shown on a terminal.
  - The event journal `events.jsonl`.
- **What the attacker cannot get, and why**:
  - The attacker **cannot** get people's private keys: per §2 (principle 5)
    these never leave the workstation and are never sent to the gateway.
  - The attacker **cannot** get machines' private registration keys:
    `state.json` holds only the public `machineKey`; the private half is
    generated locally on the machine during Set-up (§3.4, step 2).
  - The attacker **cannot** extract door keys: per §2 (principle 5) and
    §5.2, a door's private key exists only in gateway memory while the door
    is `opening`, `open` or `closing`, and never touches disk. While idle
    (`closed`, no one connected) the private key is absent even from memory.
  - The attacker **cannot** open a direct network connection to a target
    machine: machines behind NAT have no inbound ports (§1, §5.2).
- **Detection in the event journal**:
  - Passively reading an offline disk or a backup leaves no journal trace.
  - Standing up a clone gateway with the stolen host key produces tunnel
    socket collisions on active machines (§3.2: the gateway refuses a
    second instance of the same `machine:<id>`), keepalive anomalies, and
    session desynchronization.
- **Recovery procedure**:
  1. *Mechanics*: `gateway rotate-hostkey` creates a new key, and **v1 has
     no transition period** (design decision, 13.09, IAMT-152): the moment
     the gateway restarts with it, every client and machine pinned to the
     old key is refused, until the admin distributes new connection strings
     and re-registers machines. A standard rotation is by itself the
     immediate, complete revocation of a stolen key.
  2. *Emergency response*: on confirmed disk theft, run exactly that
     standard `rotate-hostkey` — it is the immediate, full removal of the
     compromised key from trust; there is no separate "emergency" path.
  3. *Updating clients*: the admin distributes new connection strings
     `iamtunnel://...#<new_fp>` (§3.1). Clients with the old string get an
     explicit `the gateway host-key fingerprint changed` error and refuse
     the session, preventing MITM.
  4. *Machine re-pinning gap*: there is no remote mechanism to update a
     machine's pinned gateway fingerprint (see Defect 6, §7). Registered
     machines refuse the new gateway and need re-registration.
  5. Audit stolen `.txt` transcripts and rotate every credential, key or
     secret that was ever shown on a terminal.

### 3.3. Compromise of gateway memory (live process hijack / root on a running gateway)

- **What the attacker gets immediately**:
  - Plaintext access to every active interactive SSH session while the
    gateway daemon is proxying it (§1, principle 3).
  - In-memory ephemeral door private keys for every machine in `opening`,
    `open` or `closing` state.
  - Active open handles to `iamtunnel-target` channels: the ability to send
    arbitrary commands straight to the local `127.0.0.1:22` Windows OpenSSH,
    bypassing gateway authorization checks.
  - **A materially larger capability since 0.3**: the ability to send
    unauthorized `door.open` directives over the always-open
    `iamtunnel-control` channel to any connected machine (`online: true`).
    An attacker controlling gateway memory can mint their own ephemeral
    Ed25519 pair and force a machine's server to open a door, bypassing
    grant checks entirely and without any person's knowledge. The machine's
    server, receiving a syntactically valid `door.open`, only checks local
    time ceilings (`maxDoorIdle`, `maxDoorHard`), starts the watchdog, and
    writes the public key to `administrators_authorized_keys`. The attacker
    then opens `iamtunnel-target` and logs in as `verifiedOsUser` with local
    administrator rights.
  - The ability to inject commands into operators' sessions and forge the
    asciicast stream before it's written to disk.
  - The gateway's host private key, from process memory.
- **What the attacker cannot get, and why**:
  - The attacker **cannot** extract people's private keys: client Ed25519/RSA
    keys sign on the client and are physically absent from the gateway's
    address space (§6.1).
  - The attacker **cannot** get a machine's private key (`machineKey`): it
    only ever lives on the target machine.
  - The attacker **cannot** override the machine's own local time ceilings:
    the server validates the received deadlines and unconditionally refuses
    `door.open` beyond `maxDoorIdle` (default 15 min) or `maxDoorHard`
    (default 8 h) (PROTOCOL §5.1). The machine also closes the door on its
    own monotonic timer regardless of anything a compromised gateway says.
  - The attacker **cannot** use the control channel to run arbitrary
    commands or touch arbitrary files on the machine: the protocol is
    limited to four operations (`door.open`, `door.close`, `door.status`,
    `door.sanitize`); `door.sanitize` only removes iamtunnel-format lines and
    is accepted only with reason `corrupted`. Any other `op`, or an attempt
    to name a path, command, content, or destination, is refused by the
    machine with `E_CONTROL_PROTOCOL`.
  - The attacker **cannot** connect to machines that are offline, powered
    off, or not running the server role (NAT/firewall still applies).
- **Detection in the event journal**:
  - An attacker with memory-manipulation tools (ptrace/gdb/shellcode) can
    suppress events.
  - Indirect signs: sessions with no preceding `auth.success`,
    `sessions`-counter desync in `state.json`, malformed `.cast` records.
- **Recovery procedure**:
  1. Immediately power off the VPS from the hypervisor console (hard reset).
  2. Destroy the compromised VM; redeploy a clean OS from a trusted image.
  3. Restart the server role on every target machine, with a `SweepStale`
     pass clearing any leftover authorized-keys lines (§3.2).
  4. Reissue the gateway's host key, re-register machines, and distribute
     new connection strings.

### 3.4. Compromise of a target machine's local administrator

- **What the attacker gets immediately**:
  - Full control of the local Windows OS: SAM, LSASS, the registry,
    processes and the `127.0.0.1` loopback interface.
  - The machine's registration private key (`machineKey`), enough to connect
    to the gateway as `machine:<id>`.
  - Read/write access to `%ProgramData%\ssh\administrators_authorized_keys`
    and OpenSSH service files.
  - The ability to kill `iamtunnel.exe` and the background `doorwatch` while
    a door is open.
  - The ability to intercept session traffic on the local `127.0.0.1:22`
    port.
- **What the attacker cannot get, and why**:
  - The attacker **cannot** reach other target machines on the network:
    machine tunnels are strictly isolated on the gateway by `machine:<id>`,
    and grants are checked per `person → machine` pair (§4.3, §5.1).
  - The attacker **cannot** get other machines' private keys or the
    gateway's host key.
  - The attacker **cannot** open inbound channels or send control commands
    to the gateway: the machine is only an SSH client; any channel-open
    attempt is refused (channel failure), and any other global request gets
    request failure (PROTOCOL §5); backed by the test
    `TestIAMT197_MachineChannelOpenAndGlobalRequestAreRefused`.
  - The attacker **cannot** modify or delete past session recordings:
    `.cast`, `.txt`, `.exec.jsonl` and the journal `events.jsonl` live on the
    remote Linux VPS, which the machine has no administrative access to
    (§1, §3.5). This holds for the standard topology — gateway and machine
    on separate hosts. When roles are combined (a machine installed on the
    same host as the gateway, SPEC §7.1), this machine's administrator is by
    definition the gateway host's administrator and reaches the records
    directly: this guarantee does not extend to a combined install (shared
    data directories are refused at startup; binding a machine to the
    gateway's own service account produces a warning from `enrol`; see
    RUNBOOK §1.3).
  - The attacker **cannot** issue their own grants in `state.json`: rights
    are only issued through the Admin role on the gateway (§3.3).
- **Detection in the event journal**:
  - A `hostkey.mismatch` result if the administrator swapped or regenerated
    the machine's OpenSSH host key.
  - Frequent tunnel drops and keepalive anomalies.
  - Invalid global requests and channel-opens from the machine are simply
    refused in v1, with **no** dedicated event; watch for connection
    anomalies instead.
- **Recovery procedure**:
  1. The gateway admin revokes the machine: `iamtunnel admin machines remove
     <id>` (§3.3). The gateway drops the machine's record from `state.json`,
     instantly closes the tunnel socket, and blocks that key from
     reconnecting.
  2. Revoke every active grant to this machine.
  3. Investigate, and reinstall the Windows OS on the target from scratch.
  4. Bring the host back with `admin machines enrol-code <name>` and repeat
     Set-up from zero (§3.4).

### 3.5. Compromise of the network path (on-path / MITM / ISP)

- **What the attacker gets immediately**:
  - Interception of encrypted traffic (passive analysis: IPs, packet sizes,
    session timing).
  - Availability attacks: TCP RST resets, blackholing, injected latency.
  - Attempts at active man-in-the-middle with a spoofed public key during
    the SSH handshake.
- **What the attacker cannot get, and why**:
  - The attacker **cannot** decrypt session traffic: sessions run over SSHv2,
    and `SPEC.md` (§5.2) and `PROTOCOL.md` (§1, §5) hard-specify the
    cryptographic policy for every connection and nested handshake: KEX
    (`mlkem768x25519-sha256`, `curve25519-sha256`,
    `diffie-hellman-group14-sha256`), ciphers
    (`chacha20-poly1305@openssh.com`, `aes256-gcm@openssh.com`,
    `aes256-ctr`), MACs (`hmac-sha2-512-etm@openssh.com`,
    `hmac-sha2-256-etm@openssh.com`), host-key algorithms (`ssh-ed25519`,
    `rsa-sha2-512`, `rsa-sha2-256`); older, weaker algorithms (SHA-1/RSA,
    DSA, ECDSA-SHA1) are unconditionally forbidden. Library defaults from
    x/crypto are never used. Every allowed set guarantees confidentiality
    and integrity.
  - The attacker **cannot** spoof public keys (MITM interception):
    - *Client to gateway*: the connection string
      `iamtunnel://...#<sha256 host key>` hard-pins the gateway key's
      fingerprint (§3.1). The client uses an isolated `known_hosts` with
      `StrictHostKeyChecking=yes`. Interactive TOFU prompts are excluded; a
      mismatch ends the session with `the gateway host-key fingerprint
      changed`.
    - *Machine to gateway*: the gateway's fingerprint is baked into the
      one-time registration code `iamtunnel-enrol://...#<sha256 host
      key>:<secret>` (§3.4, step 1); checked automatically before the secret
      is sent.
    - *Gateway to machine*: the target's `sshdHostKey` is pinned by the
      gateway at verification (§3.4, step 3) and strictly checked in
      `HostKeyCallback` (§5.2); a mismatch blocks the session and sets
      `hostkey-mismatch`.
- **Detection in the event journal**:
  - `hostkey.mismatch` events on an interception attempt between machine and
    gateway (§5.2).
  - Abnormal keepalive failure counts and TCP connection drops.
- **Recovery procedure**:
  1. The cryptographic pins automatically defeat MITM attempts, with no
     human action needed.
  2. For sustained availability attacks (RST flood, port blocking), switch
     network routes, change the gateway's external port (`--port`, §3.5), or
     run a VPN tunnel between the VPS and the target network.

### 3.6. Malware on a client workstation

- **What the attacker gets immediately**:
  - Access to the locally generated client private key
    (`%LOCALAPPDATA%\iamtunnel\key`), which per §3.1's design is stored
    **without a passphrase**, owner-only permissions.
  - Access to the current user session's `ssh-agent` socket.
  - The ability to authenticate to the gateway from any other host as the
    compromised person (`person`).
  - The ability to inject into the terminal emulator process to capture
    output or inject stdin.
  - Access to the local cache of allowed machines (`machines.mine`, §3.1).
- **What the attacker cannot get, and why**:
  - The attacker **cannot** connect to machines the person has no grant for
    in `state.json` (§5.1: refused with `E_SESSION_DENIED` /
    `E_GRANT_MISSING`).
  - The attacker **cannot** outlast the access window: the grant's `until`
    is enforced by the gateway's clock (§6.4).
  - The attacker **cannot** hide the session from recording: it goes through
    the gateway and is captured in `events.jsonl`, `.cast` and `.txt` (or
    `.exec.jsonl`) (§1, principle 3).
  - The attacker **cannot** get other people's keys or machine registration
    keys.
- **Detection in the event journal**:
  - `auth.success` events from unusual external addresses for the person.
  - Hitting the per-person session limit (`E_SESSION_LIMIT_PERSON`,
    PROTOCOL §1.4).
  - Attempts against machines with no active grant (`session.drop`).
- **Recovery procedure**:
  1. The gateway admin immediately removes the person's key:
     `admin people keys remove <person> <fingerprint>` (§3.3).
  2. Force-kill every active session for that person: `admin sessions kill
     <id>`.
  3. Revoke active grants: `admin grants revoke <person> <machine>`.
  4. Clean the workstation, generate a new key pair, and have the admin add
     the new public key.

### 3.7. Model 1: an external attacker on the Internet (online guessing & brute force)

- **Attack vector and attempts**:
  - The attacker scans the gateway's TCP 2222 port, probing for OpenSSH/Go
    vulnerabilities or trying to guess credentials.
  - *Risk analysis of MaxAuthTries = 32*: §6.1's raised auth-attempt limit
    (32, vs. OpenSSH's default 6) exists for convenience with large
    ssh-agent key sets, but widens the online guessing budget per TCP
    connection by 5.3×.
  - *How the rate-limit gap was closed in 0.3/v1*: earlier drafts limited by
    (IP, fingerprint) alone, which let an attacker stream random,
    unregistered keys without ever tripping the limiter. `SPEC.md` (§6.1),
    `PROTOCOL.md` (§1.4) and the code now split the logic: before signature
    verification, the gateway classifies the presented key against the
    state snapshot. Failed `unknown-key` attempts are counted **strictly per
    remote address** (10 in 5 minutes triggers a 15-minute IP ban with
    `E_AUTH_RATE_LIMITED`); a registered key's failures (`known-key`) are
    counted by `(remote-address, fingerprint)`, so one office's NAT isn't
    locked out by one employee's mistake.
- **What the attacker cannot get, and why**:
  - The attacker **cannot** authenticate by password: password auth is fully
    disabled on the gateway (§6.1, public keys only).
  - The attacker **cannot** brute-force an Ed25519 private key: 256-bit
    elliptic-curve strength ($2^{128}$) rules out practical guessing.
  - The attacker **cannot** bypass the rate limit by generating fresh keys
    from one address.
  - The attacker **cannot** reach an interactive shell on the gateway
    itself: `PublicKeyCallback` is a pure function with no side effects, and
    the gateway only serves authorized machine sessions and protocol exec
    commands.
- **Detection in the event journal**:
  - Bulk failed-login events: `auth.failure {address: "...",
    fingerprint: "..."}`. Since R4 F-11 (24.09.2026), same-cause failures
    from one host are folded: one line per quiet period
    (`AuthSuccessQuiet`, 10 minutes) with the first attempt's reason, and a
    summary line at the period's end with `details.repeats`/`firstRepeat`/
    `lastRepeat` — the scan is still just as visible, and the journal is no
    longer a place a connection flood can fill one line at a time (before
    the fix this was a disk-fill path and produced `E_AUDIT_UNAVAILABLE` for
    everyone, IAMT-451). Slow brute force (attempts spaced out beyond the
    quiet period) still gets one line per attempt.
  - The rate limiter firing: `auth.failure` with a result like `rate limited
    until ...` (`{address: "..."}`); a post-ban attempt burst in the quiet
    period is folded the same way, plus the ban event itself.
  - Connection-setup timeout records (`E_SESSION_SETUP_TIMEOUT`, PROTOCOL
    §1.4).
- **Response procedure**:
  1. Block the attacking IP ranges at the Linux VPS firewall
     (`nftables`/`iptables`).
  2. Change the gateway's external port (`--port`, §3.5).

### 3.8. Model 2: a person with valid, expired, or revoked access

- **Attack vector and attempts**:
  - A former employee or contractor, holding a saved private key and
    connection string, tries to start an SSH session after the grant's
    `until` has passed, or after `admin grants revoke`.
  - Attempting to keep persistence through processes started during a
    legitimate session before revocation.
- **What the attacker cannot get, and why**:
  - The attacker **cannot** open a new session to the machine: per §5.1,
    after a successful `PublicKeyCallback`, the gateway checks for an active
    `grant{person, machine, until}` tuple in `state.json`.
  - The deadline is checked strictly against the gateway's synchronized
    clock (UTC, `timesyncd`, §6.4); the client's system clock is irrelevant.
  - Without an active grant, the gateway instantly refuses with the single
    text `Access to this machine is currently unavailable.\r\n`, journals a
    `session.drop` with an internal `E_GRANT_EXPIRED` / `E_GRANT_MISSING`
    code, and closes the transport. No reservation is created, no
    `door.open` is sent over `iamtunnel-control`, and the door in
    `administrators_authorized_keys` stays closed.
  - If a grant is revoked (`admin grants revoke`) mid-session, per §6.4 and
    §12 the gateway immediately tears down the `session` channel and, if no
    other sessions remain, sends `door.close` over `iamtunnel-control`.
- **Residual risk (see Defect 4 in §7)**:
  - Closing the network channel doesn't end background processes the
    operator may have started (a service, a scheduled task) under the local
    administrator account `verifiedOsUser` before revocation.
- **Detection in the event journal**:
  - `session.drop` records naming the person, machine, address and key
    fingerprint.
- **Response procedure**:
  1. Permanently remove the person's public key:
     `iamtunnel admin people keys remove <person> <fingerprint>` (§3.3).
  2. Have the admin check the target machine's process and service list for
     any leftover background tasks.

### 3.9. Model 3: a person with access to machine A seeking access to machine B

- **Attack vector and attempts**:
  - A legitimate user with a grant on machine A tries lateral movement by
    substituting machine B's name in the SSH request
    (`person:machineB@gateway`).
  - Trying to hijack an already-open door on machine B while another
    legitimate operator is working there.
- **What the attacker cannot get, and why**:
  - The attacker **cannot** connect to machine B through the gateway: the
    gateway takes the verified `person` from the successful handshake's
    `Permissions` and checks for a grant on exactly the requested pair
    `grant{person, machineB, until}` (§4.3, §5.1). A missing grant gives an
    unconditional refusal with the single message `Access to this machine is
    currently unavailable.\r\n` (outward `E_SESSION_DENIED`, internally
    `E_GRANT_MISSING`, a `session.drop` event), without revealing machine
    B's status.
  - The attacker **cannot** ride someone else's tunnel: each machine's
    tunnel is strictly isolated in the gateway's `id -> ServerConn` registry
    (§5.2). Opening an `iamtunnel-target` channel only happens inside the
    specific machine's socket named in the verified grant.
  - Even if machine B's door is currently open for someone else
    (`sessions > 0`), the gateway does not create an SSH client to machine
    B's `127.0.0.1:22` for an unauthorized person.
- **Detection in the event journal**:
  - Access-denial records: `session.drop` with `E_GRANT_MISSING`
    (`person: "...", machine: "machineB"`).
- **Response procedure**:
  1. Log a security incident with monitoring.
  2. Temporarily suspend the user's rights if signs point to deliberate
     scanning of the machine fleet.

### 3.10. Threat: intercepting a machine's one-time enrollment code

- **Attack vector and mechanism**:
  - A machine invitation is generated by an admin via
    `admin machines enrol-code <name>` (§3.3, §7.2; since 1.4 with a single
    argument, the name — the admin never enters an OS user, the machine
    reports it itself) in the form
    `iamtunnel-enrol://<host>:<port>#<sha256 host key>:<secret>`. **Lifetime
    is 15 minutes** (§3.4, since 1.3; was 24 hours).
  - The code is a one-time bearer secret, carried to the target machine's
    engineer over an external channel (email, ticketing, chat).
  - An attacker intercepts it in an unprotected channel before it's used on
    the real target machine. The window shrank from a day to 15 minutes: the
    old day-long secret sitting in a message or ticket was this scheme's real
    weakness. Splitting the invitation across separate channels is **not**,
    and never was, a defense — it assumed an attacker who reads exactly one
    of two channels, and in practice a second channel never shows up
    (design decision, 2026-09-17, SPEC §3.6).
- **Attack progression and impact**:
  1. The attacker runs `iamtunnel enrol <intercepted code>` on a host they
     control.
  2. The attacker's host connects to the gateway, which validates the
     secret, creates a `machine{state: enrolled, osUserStatus: pending}`
     record and stores the attacker's machine's public key (§3.4, step 2);
     the secret burns in `state.json`.
  3. The attacker's host raises a tunnel to the gateway (§3.4, step 3).
     **Since 1.3, `requestedOsUser` and the machine's name come from the
     machine itself**, not from an admin-time binding — so the attacker
     freely names an account they already control, and the probe against it
     succeeds. The machine's name is not chosen by the attacker either
     (since 1.4) — it was written into the invitation by the admin's own
     hand. The gateway opens `iamtunnel-target`, captures and pins the sshd
     host key, then temporarily opens the door and runs an SSH public-key
     user-auth probe as `requestedOsUser`. If the attacker hasn't set up a
     matching Windows account in local administrators, the probe fails
     (`osUserStatus: rejected`, `enrol.failed`), and the machine stays
     blocked in `enrolled`. If the attacker fully impersonated the account,
     the machine moves to `state: verified`.
  4. When the legitimate admin tries the code on the real machine, the
     registration fails: the secret is already burned
     (`E_ENROL_SECRET_USED`).
  5. *Critical consequence*: on a successful impersonation, the gateway
     admin, believing the machine registered correctly, issues grants to
     engineers, who then land on the attacker's server instead.
- **Detection in the event journal**:
  - Machine registration from an unusual external IP: the `enrol` step and
    tunnel raised from a suspicious host.
  - Repeated failed `enrol` attempts from the legitimate machine's IP,
    reporting a used code (`enrol.failed` → `E_ENROL_SECRET_USED`).
- **Prevention and recovery**:
  1. Immediately revoke the compromised machine: `iamtunnel admin machines
     remove <id>`.
  2. Shorten the one-time code's TTL — **done in 1.3: 15 minutes** (owner's
     decision, 2026-09-17, SPEC §3.4, §3.6). Operational consequence for the
     admin: issue the invitation when the engineer is already standing at
     the machine, not a batch in the morning.
  3. The admin should compare the machine's external IP and its public
     key's fingerprint before issuing the first grants. Since 1.3, this also
     means checking the **hostname and OS account the machine itself
     claims**: they arrive from the machine, are flagged "new" in the list,
     and are removable with one button (§3.4, §7.1). A self-declared name
     grants no rights on its own — but it's exactly what the admin must
     compare against expectations by eye before issuing the first grant.

### 3.11. Threat: denial of service via recording-disk exhaustion

- **Attack vector and mechanism**:
  - SPEC §3.5 states a hard rule: *"Disk above threshold → new sessions are
    refused with a clear message and an event; access without recording is
    never allowed (principle 3)."*
  - An attacker with legitimate (or compromised) access to at least one
    target machine deliberately generates a huge volume of terminal output
    (e.g. an infinite data generator).
  - The `.cast`, `.txt` and `.exec.jsonl` files under
    `/var/lib/iamtunnel/recordings/` grow at network speed.
- **Progression and defense in v0.3/v1**:
  1. `PROTOCOL.md` (§8) introduces a strict threshold split, keeping rotation
     from colliding with a sudden access refusal.
  2. At **85% fill**, background rotation by age kicks in (deleting
     recordings older than 90 days), then the oldest recordings are removed
     until fill drops below 85% (each deletion is journaled).
  3. Refusing new sessions uses a separate `recordingRefusePercent = 95%`
     threshold. The 85–95% window gives cleanup room to work.
  4. If the write rate outpaces cleanup and the disk passes 95%, the gateway
     returns `E_RECORDING_DISK_FULL` before opening the session, protecting
     the system disk and the audit journal from overflow.
- **Detection in the event journal**:
  - Rotation-by-place deletions: `admin.op` lines with
    `result:"rotation.prune"`, one per deleted session, with the session's
    path in `object`.
  - Sessions refused past the 95% threshold: `session.drop` with `result`
    starting `recording: disk full beyond refuse threshold` (the internal
    code `E_RECORDING_DISK_FULL` is never written literally).
  - Abnormal byte-count growth in `sessions.active`.
- **Prevention and recovery**:
  1. Force-kill the anomalous attacker's session: `admin sessions kill <id>`.
  2. Put `/var/lib/iamtunnel/recordings/` on its own isolated volume, so
     filling it doesn't touch system files, `state.json` or `events.jsonl`.
  3. Introduce a per-session data-volume quota.

### 3.12. Linux-machine threats (v1.1, SPEC §3.2.1)

A Linux machine differs from the Windows machine of §3.2 only in the
platform layer: the door file is a foreign user's
`<osUser-home>/.ssh/authorized_keys`, the server role runs as root, and the
watchdog detects the parent's death through the kernel (`pidfd`) rather than
a process handle. What follows is what this layer adds to the threat model;
every other threat in §3 stands unchanged ("Everything said about §3.2 …
applies without change").

#### 3.12.1. Foreign lines in `~/.ssh/authorized_keys` (byte-for-byte preservation)

- **Asset.** `~/.ssh/authorized_keys` for `osUser` is **not our file**: it
  holds other people's and service accounts' personal keys, and it's also
  the door's write target. The value at risk isn't the door line — it's
  every other line: losing or reformatting them revokes someone else's
  legitimate access, and "quietly rearranged" lines make any incident review
  useless.
- **Vector and mechanism.** Two naive implementations are dangerous: (a)
  "read the whole file, filter, rewrite" — this corrupts other lines through
  sorting, whitespace normalization, lost comments, collapsed duplicate
  keys, or changed line endings; (b) removal by "looks similar" instead of an
  exact marker — this can catch a foreign line, and the person silently
  loses access.
- **Mitigation (§3.2.1, PROTOCOL §5).** The door line is marked with
  `iamtunnel-door=<id>` in its trailing comment. Writes are an atomic
  replace relative to a directory descriptor (`openat`/`renameat`,
  `O_NOFOLLOW`), a temp file in the same directory, owner `osUser`, mode
  `0600`, `fsync`, read-back; `door.close` removes exactly its own line by
  id; `SweepStale`/`door.sanitize` remove only marker-prefixed lines
  (including corrupted ones), and everything else is kept **byte-for-byte,
  in order**. A symlink on `~/.ssh` or on the file itself is refused, not
  followed — otherwise root would write the key wherever the attacker
  pointed.
- **Detection.** `Op:"open"|"close"|"sweep"` in the machine's local journal
  (`/var/lib/iamtunnel-machine/events.jsonl`), `Removed`/`CorruptRemoved`
  counters on sweep; on the gateway, `door.open`/`door.close`/
  `door.sanitize`. A practical integrity check is comparing the file against
  a copy taken beforehand (RUNBOOK §6, item 9; §5.9).

#### 3.12.2. StrictModes refusals (fail-closed)

- **Asset.** A door only exists as much as sshd accepts it: with
  `StrictModes yes` (the default), OpenSSH ignores `authorized_keys` if the
  home directory, `~/.ssh`, or the file itself are group/world-writable, or
  owned by anyone but `osUser` or root.
- **Vector.** (a) Silent refusal: the line is written, the key is in place,
  but login fails — both the person and the admin look everywhere except
  permissions. (b) Auto-"fixing" permissions: iamtunnel runs as root and
  could `chmod`/`chown` the directory into shape, but that hides the real
  cause (e.g. the home directory belongs to someone else on purpose) and
  overrides what the machine's admin configured deliberately.
- **Mitigation.** Two preflight checks: `sshd -T -C user=<osUser>` confirms
  `pubkeyauthentication yes` and that `authorizedkeysfile` includes
  `.ssh/authorized_keys` (otherwise refuse, hinting at `--key-file`), and
  StrictModes' own requirements on the home directory, `~/.ssh` and the file
  are checked **before** writing; a violation refuses `door.open` with a
  clear message (§3.2.1). Fail-closed behavior: the door doesn't open, but
  no foreign key gets in either, and iamtunnel never rewrites the home
  directory's permissions.
- **Residual risk.** Editing `sshd_config` after install (e.g. a different
  `AuthorizedKeysFile` path) can steer sshd away from the file the door
  writes to; the same preflight check surfaces this, fixed with `--key-file`
  or a re-enrol.

#### 3.12.3. Running as root

- **Why.** The door file belongs to `osUser`, but root writes to it: only
  root can create `~/.ssh` with the right owner, replace the file
  atomically, and hold `door.lock` in the server's data directory so the
  user themselves can't release it. The machine's data directory
  `/var/lib/iamtunnel-machine` is `0700`, owned by root
  (`machine.key` `0600`); the systemd unit runs `User=root` (SPEC §3.2.1).
- **Threat.** Compromising the server process means root on the machine:
  deleting or replacing foreign `authorized_keys` lines, reading the
  machine's journal, planting one's own line. The core invariant (§2.4)
  still holds: the door key's private half never exists on the machine at
  all — it lives only in gateway memory (layer 1) — so a line left in the
  file is inert; but local root access is already a machine compromise, not
  just a door compromise.
- **What limits it.** Every role command (`enrol`,
  `server start|stop|status|install|uninstall`) requires root (euid 0) and
  refuses with a `sudo` hint otherwise, with no silent elevation; a person
  logs into the machine as `osUser`, not root, and iamtunnel never grants
  `sudo`. The systemd unit is hardened (`ProtectSystem=full`,
  `NoNewPrivileges=yes`, `PrivateTmp=yes`, `KillMode=mixed`) and
  **deliberately without** `ProtectHome`: the door writes to
  `<osUser-home>/.ssh/authorized_keys`, and `ProtectHome=yes` would make
  `/home` unreachable and the door would never open (rationale — RUNBOOK
  §1.7). The data directory (`0700`) and directory-descriptor-relative
  writes close the "symlink swap mid-write" path.
- **Residual risk.** The same as §3.4: a machine's local administrator is a
  trusted subject; root access gives them what they already have by
  definition.

#### 3.12.4. The door watchdog (`doorwatch`) on Linux

- **Contract (SPEC §6.3, §3.2.1).** The watchdog is a separate process in
  its own session (`setsid`), started **before** the door line is written.
  It waits for the parent's death via `pidfd_open` + `poll`, or on kernels
  without pidfd, `PR_SET_PDEATHSIG` with an immediate `getppid()` check right
  after setting it (closing the race where the parent dies between `fork`
  and the signal being armed). On the parent's death, the watchdog removes
  the line under lock and journals it on the machine. After a confirmed
  `door.close`, the server stops the watchdog by its saved pidfd, not by
  PID — a PID can be reused, a pidfd points at the exact process; a failure
  to stop the watchdog is logged locally and doesn't undo the close
  (`removed:true` still stands).
- **What threat it closes.** A server crash while the door is open (matrix
  Scenario 3, §5): without the watchdog the line lives until the next server
  start (Scenario 3b); with it, the window shrinks to a fraction of a
  second. Compromising the watchdog itself grants nothing: it holds no
  private half of the key, and its only ability is removing marker-tagged
  lines under lock.
- **Difference from Windows.** There, the watchdog waits on the parent
  process handle's signaled state (`WaitForSingleObject`); on Linux, a pidfd
  event from the kernel. Its own session (`setsid`) is the direct analogue
  of `CREATE_BREAKAWAY_FROM_JOB`: it takes the watchdog out of the server's
  process group so a group kill (`killall iamtunnel`, `kill -9 -<pgid>`,
  systemd's timeout `SIGKILL` to the whole group) doesn't take it down with
  the server — this is the difference between Scenarios 3 and 3b.
- **Implementation details (IAMT-247, IAMT-263).** On Linux the watchdog
  opens the parent's pidfd (`pidfd_open`, kernel 5.3+) and waits in `poll`
  windows of 500 ms. Without pidfd support (`ENOSYS`, Linux < 5.3), it
  doesn't refuse — it falls back per SPEC §3.2.1 to `PR_SET_PDEATHSIG` with
  a catchable `SIGTERM`, used only as an early wake-up; the actual death
  decision comes from polling `getppid()`. `SIGKILL` is deliberately never
  used as the PDEATHSIG (IAMT-279): it's delivered by the kernel at the
  moment the pidfd becomes readable, is uncatchable, and could end the
  watchdog before it removes the line — and the server's own layer 2 does
  nothing on `kill -9` either. The same decisions apply on macOS (IAMT-263):
  `kqueue` + `EVFILT_PROC`/`NOTE_EXIT`, treating `ESRCH` at registration as
  "parent already dead, clean up", and `EV_ERROR` while waiting as an error,
  not an exit.
- **Build status (2026-09-15).** The watchdog is merged for Linux
  (IAMT-247) and macOS (IAMT-263); `door.open` works on both Unix
  platforms. A server crash with the door open is Scenario 3 (a fraction of
  a second), not 3b.

### 3.13. Mac-machine threats (v1.1, SPEC §3.2.1)

A macOS machine differs from the Linux machine of §3.12 only in the
platform layer: sshd runs as the launchd job `com.openssh.sshd`, gated by
the Remote Login switch, without a `sshd.service`/systemd daemon or
`/etc/ssh/sshd_config` as the sole source of truth (macOS sshd is still
queried the same way, via `sshd -T`); the door file is
`<osUser-home>/.ssh/authorized_keys`, as on Linux; TCC blocks writes into
Desktop/Documents/Downloads/iCloud Drive; the machine role runs as root
(LaunchDaemon has no "unprivileged" form the way Linux does); and the
watchdog detects the parent's death via kqueue rather than pidfd. What
follows is what this layer adds; every other threat in §3 and §3.12 stands
unchanged.

#### 3.13.1. Remote Login (the launchd job `com.openssh.sshd`)

- **Asset.** The door's precondition: sshd listens on `127.0.0.1:22`,
  answers `sshd -T`, and accepts pubkey auth for the machine's OS user. On
  macOS, sshd is a launchd job labeled `com.openssh.sshd`; it's up if and
  only if Remote Login is turned on in System Settings → General → Sharing.
- **Vector.** A disabled Remote Login gives "connection refused" — the same
  symptom as a dead sshd on Linux. The on-call engineer looks in the wrong
  place; the person in the GUI sees "connect failed", not "turn on Remote
  Login".
- **Mitigation (SPEC §3.2.1, IAMT-264).** The preflight check runs the same
  way as on Linux (`sshd -T -C user=<osUser>`), and the platform-specific
  service check asks launchd directly; if the job isn't loaded, refuse with
  a literal hint: `the Remote Login daemon is off: launchd has no
  com.openssh.sshd job — turn it on in System Settings → General → Sharing
  → Remote Login (or run "sudo systemsetup -setremotelogin on") and start
  again`.
- **What limits it.** The same hint text is used by both `enrol` and
  `server start`, so the two paths can't drift apart.
- **Residual risk.** Renaming or disabling `com.openssh.sshd` (an
  unsupported edit of `/System/Library/LaunchDaemons/ssh.plist`, or
  switching to a Homebrew `openssh` with its own plist) steers sshd away
  from this preflight check: the symptom looks the same, but the cause
  isn't the switch. The watchdog doesn't help here — it works at the door
  layer, not sshd's.

#### 3.13.2. sshd StrictModes (fail-closed, as on Linux)

Same asset, vector, mitigation and residual risk as §3.12.2: `StrictModes
yes` is the default on macOS's OpenSSH too, and the same preflight check and
fail-closed behavior apply, using the same refusal text.

#### 3.13.3. TCC / Full Disk Access on the key file

- **Asset.** The door key file is wherever iamtunnel writes the public-key
  line — by default `<osUser-home>/.ssh/authorized_keys`, or anywhere
  `--key-file` names. Desktop, Documents, Downloads and iCloud Drive sit
  behind TCC (Transparency, Consent, and Control), which an ordinary process
  can't write to even as root, since TCC checks live in TCC.db and don't
  depend on euid.
- **Vector.** Two variants of the same mistake: (a) an operator points
  `--key-file` at a protected folder and gets `EPERM`, read as a Unix
  permissions problem when the real cause is TCC; (b) the door file ends up
  in iCloud Drive, and sync makes the line appear and disappear on other
  devices — the private half on the gateway stays the same, but the public
  line is drifting across someone else's disks.
- **Mitigation (IAMT-264).** A hint is printed **before** the refusal,
  naming Full Disk Access as a conditional fix (needed only when the key
  file is in a protected folder) — the ordinary `~/.ssh` location doesn't
  need it at all.
- **What limits it.** iamtunnel never requests Full Disk Access
  programmatically — a human grants it in System Settings; the product also
  never writes the door line outside the file it means to write, using
  file-descriptor-relative operations (`openat`, `O_NOFOLLOW`), as on Linux
  (§3.12.1).
- **Residual risk.** iCloud Drive syncs `.ssh` like everything else — that's
  the Files provider, not TCC; pointing `--key-file` at a synced folder
  means the door line travels with the sync. This is documented as "don't do
  this" (RUNBOOK §6, item 3a), but the code can't forbid it: `--key-file`
  hands the responsibility to the operator.

#### 3.13.4. LaunchDaemon for `server start` under root

- **Why.** Same reasoning as Linux (§3.12.3): the door file belongs to
  `osUser`, and root writes to it. On macOS a LaunchDaemon with no
  `UserName` key runs as root by default, and there's no "unprivileged" form
  for the machine role the way Linux has a service user. `_iamtunnel` exists
  only for the gateway role (§3.13.8), not the machine role.
- **Threat.** Same as §3.12.3: compromising the server process means root
  on the machine. The core invariant (§2.4) is unaffected — the door key's
  private half only ever lives in gateway memory.
- **What limits it.** Every role command requires root and refuses
  otherwise with the platform's own elevation hint; a person logs in as
  `osUser`, not root; `sudo` is never granted by iamtunnel. The machine's
  LaunchDaemon is rendered by the same plist template as the gateway's, but
  with an empty `UserName` (root) and `KeepAliveOnCleanExit: false` (the
  macOS analogue of systemd's `Restart=on-failure`: an ordinary `server
  stop` must not be undone by a restart).
- **Residual risk.** Same as §3.4 and §3.12.3: a machine's local
  administrator is a trusted subject.

#### 3.13.5. The door watchdog (`doorwatch`) on macOS — kqueue EVFILT_PROC/NOTE_EXIT

- **Contract (SPEC §6.3, §3.2.1, IAMT-263).** The watchdog is a separate
  process in its own session (`setsid`), started **before** the door line is
  written, as on Linux. macOS has no `pidfd_open(2)`; the watchdog instead
  registers the parent's PID on kqueue with `EVFILT_PROC`/`NOTE_EXIT`, then
  blocks in `kevent` in 500 ms windows. `NOTE_EXIT` fires on any exit,
  `SIGKILL` included — the same "the watched object is gone" signal pidfd
  gives Linux.
- **What threat it closes.** Same as Linux (§3.12.4): a server crash with
  the door open shrinks from Scenario 3b (until the next start) to Scenario
  3 (a fraction of a second).
- **Difference from Linux.** No `PR_SET_PDEATHSIG` fallback exists on
  macOS; instead, a `maxWait` deadline and the server's own layer 2 provide
  the backstop. Its own session (`setsid`) plays the same role as on Linux
  and Windows: it survives a launchd job teardown
  (`launchctl bootout system/com.iamtunnel.machine`) that kills the rest of
  the job's processes.
- **Implementation details (IAMT-263).** kqueue registration happens once,
  so a reused PID can't misfire on the old note. If the parent is already
  dead at registration time, `kevent` returns `ESRCH`, treated as "already
  gone, clean up" — mirroring the Linux side. `EV_ERROR` while waiting is an
  error, not an exit.
- **Build status (2026-09-15).** Merged (IAMT-263,
  `internal/winkeys/doorwatch_darwin.go` +
  `internal/winkeys/doorwatch_unix.go`); `door.open` works on both Unix
  platforms.

#### 3.13.6. `osascript ... with administrator privileges` — quoting and data flow

- **Why.** macOS has no UAC equivalent; the standard path for "this needs
  root for one button" is `osascript -e 'do shell script "<cmd>" with
  administrator privileges'`: SecurityAgent shows the standard prompt, and
  on approval macOS runs the command as root. The password never reaches
  iamtunnel — it only learns whether the human agreed.
- **Vector.** Three easy ways to shoot yourself in the foot: (a)
  concatenating a command with unescaped input; (b) wrapping the command in
  double quotes without escaping, letting an embedded quote break the
  AppleScript string literal; (c) leaving standard streams connected, so
  `do shell script` waits for them to close and `osascript` hangs.
- **Mitigation.** Two independent escaping layers in `internal/macos`: shell
  quoting (POSIX single-quote wrapping, with the standard `'\''` escape for
  an embedded quote) makes any string exactly one shell word, immune to
  `$`, backticks, `;`, `&&`, `|`; then AppleScript quoting escapes only `\`
  and `"`, and refuses (rather than silently rewrites) any control character
  it can't represent exactly. The command is disconnected from standard
  streams and invoked via `exec`, not a nested shell, closing the hang and
  the "second parser" risk at once.
- **Residual risk.** A human approving the prompt without reading the
  command is a SecurityAgent design limitation iamtunnel can't work around.

#### 3.13.7. The Connect button: a temporary shell script, not an AppleScript literal

- **Mitigation.** The Connect button writes a small, mode-0700 temporary
  shell script (`os.CreateTemp`, `O_EXCL`) containing a fully shell-quoted
  `exec 'iamtunnel' 'client' 'connect' '<machine>'`, then asks Terminal.app
  to run that file — never building an AppleScript string with the machine
  name spliced into a literal. This keeps the number of parsers the machine
  name crosses down to one (the shell script itself), with `config.ValidName`
  as an independent first check.
- **Residual risk.** Purely theoretical: `os.CreateTemp`'s `O_EXCL` and mode
  0700 rule out guessing or pre-creating the file.

#### 3.13.8. The service user `_iamtunnel` and symlink-safe ownership changes

- **Why.** The gateway role on macOS runs as `_iamtunnel`, not root: a
  hidden, freely chosen system UID below 500, shell `/usr/bin/false`, group
  `staff`, created once via `dscl`. This is the same least-privilege shape
  as the Linux gateway's dedicated systemd user.
- **Threat.** A naive recursive `chown` could follow a symlink planted
  inside the data directory and hand ownership of whatever it points to the
  service account, or race a directory-to-symlink swap mid-walk (TOCTOU).
- **Mitigation (IAMT-291).** Every directory entry is classified before it's
  ever opened (`Lstat`/`Fstatat` with `AT_SYMLINK_NOFOLLOW`); only regular
  files and directories are opened at all, via `Openat` with `O_NOFOLLOW`; a
  symlink is refused outright, with a message naming the exact path. All
  further action happens through the already-open file descriptor, not the
  path, closing the classic race window between checking a path's type and
  acting on it. A regular file with more than one hard link, or a directory
  tree deeper than a bounded limit, is also refused — either could reach
  outside the intended tree or exhaust file descriptors.
- **Residual risk.** If an attacker is already root on the host (or already
  has write access to the parent of the gateway's data directory) before
  install ever runs, they could plant a symlink ahead of time — but that
  attacker already has full root, which is outside what this product
  defends against.

#### 3.13.9. The log directory `/Library/Logs/iamtunnel`

- **Asset.** Both the gateway's and the machine's LaunchDaemon need
  `StandardOutPath`/`StandardErrorPath` to point at a file in an existing
  directory — launchd itself never creates directories. Both roles use
  `/Library/Logs/iamtunnel`, handed to the service user so the daemon can
  write without root.
- **Residual risk.** The directory outlives an uninstall (by design, so a
  later reinstall keeps the same identity) and is on the operator to clean
  up. On a full disk, launchd's own failure to write ends up in
  `/var/log/com.apple.xpc.launchd/launchd.log`, not
  `/Library/Logs/iamtunnel/gateway.log`.

### 3.14. Ask mode: a boundary against carelessness, not against someone who knows the bypass

Under `ask`, a red command never reaches the machine until a separate
`risk.approve` action arrives — signed with the same key that signed the
command itself. Read this plainly: at the gateway's level, "a human
approved" and "an AI agent on the same machine approved" are
indistinguishable, because both travel under one key. Approval is one-time,
tied to an exact person, machine and command string, expires in 5 minutes,
and is journaled as a separate `risk.approval` event.

So the honest boundary is this. `ask` defends against carelessness and
accident: a command that briefly caught a human eye before running, a
script that took the wrong branch, an automated run that used to reach the
machine silently. It does NOT defend against someone who knows about
`risk.approve` and the approval queue: such an AI agent on the same machine
approves itself, and the gateway cannot tell the difference. "The AI will
ask its user" is a convention, not an enforcement mechanism — the gateway
cannot compel an agent to ask. An administrator, or a human who genuinely
wants to cause harm, is likewise not this defense's subject. The only
reliable enforcement is: the command doesn't pass without a further action
under the same key, and one approval covers exactly one exact run. A
gateway restart discards pending approvals. There is no live wait inside the
SSH session, so a hung automation never pins down a gateway resource.

### 3.15. The external command classifier: decision source, privacy, and failure

The classification source is set by `risk_classifier`: `rules` (default),
`ai`, or `both`. In `ai` the external classifier is the deciding source; in
`both` the result is the stricter of local and external verdicts. A score
above the 0.85 threshold gets the stable rule name `external-classifier`, so
the warning, `session.risk`, and status all show that a red verdict came
from the external source. The UI is never this decision's source — an
operator confirms `classifier=...` through gateway status and the journal.

- **Privacy**: for every `ai`/`both` exec, the command passes a scrubber
  immediately before the external call; secrets in arguments or environment
  variables must never leave the gateway. Interactive shell input is never
  sent to the external service. The residual risk is a new secret shape the
  scrubber doesn't yet recognize — closing that gap needs growing the local
  canary test set.
- **Latency and availability**: the synchronous wait is capped at 800 ms. If
  local rules in `both` already produced red, the gateway decides
  immediately and the external call proceeds asynchronously for the audit
  trail — this keeps the refusal in place without waiting on the external
  result.
- **External-service failure**: in `both`, the safe fallback is the local
  verdict, with one warning line and `session.risk` recording the external
  failure. In `ai`, the failure is fail-closed: the exec stops before
  reaching the machine with `E_RISK_CLASSIFIER_UNAVAILABLE`, and a separate
  `session.drop` records the operational refusal. The reason distinguishes
  an invalid/expired key (`401/403`) from an unreachable service
  (timeout/`5xx`). The human is offered `risk_classifier: "rules"` or
  `"both"` with a restart, or an explicit downgrade via
  `iamtunnel admin risk mode log`/`warn`.
- **Trust in the provider**: the external service sees scrubbed commands and
  influences blocking in `ai`/`both`, so a lost key, a changed endpoint, or a
  malformed reply are the provider's own risk. The key lives only in the
  gateway's external configuration and must never end up in source code,
  tests, reports or logs.

### 3.16. Unprivileged code under the same account hijacking a machine's registration (R4, F-04)

Separate from §3.4 — there the attacker already owns the machine outright;
here, code running with an ordinary account's rights moves to elevated
rights by swapping out the registration itself. On Windows, the logon task
(§3.2.2, `InteractiveToken` + `HighestAvailable`) runs `server start` with
the account's highest token and no UAC prompt, and that elevated start reads
which gateway to call, which fingerprint to pin, and which machine id to
claim from the personal directory `%LOCALAPPDATA%\iamtunnel\server`. Locking
down the directory itself (IAMT-213) isn't enough: an unprivileged process
under that same account still holds `FILE_DELETE_CHILD` on the parent
`%LOCALAPPDATA%\iamtunnel`, and that right on the parent lets it rename the
child directory regardless of the child's own DACL. The substitution: rename
`server` to something else, drop in a new `server\` with its own
`enrolment.json` (an attacker's gateway and fingerprint) and a new
`machine.key`, then wait for the next logon. The elevated start then dials
the attacker's gateway, and its `door.open` writes the attacker's key into
`%ProgramData%\ssh\administrators_authorized_keys` — an unprivileged process
turns into a permanent, full-administrator remote entry that survives
deleting the tampered directory.

- **What holds it.** A "registration anchor": `enrol` writes a copy of the
  registration's routing facts (host, port, fingerprint, machine id) to
  `%ProgramData%\iamtunnel\anchors\<SID>\enrolment.anchor.json` — from the
  values held in memory, not from a re-read of the profile directory —
  under a tree locked the same way as the machine's data directory, and
  `%ProgramData%` doesn't grant ordinary accounts the right to delete or
  rename its children. An elevated `server start` refuses to act until the
  profile record and the anchor agree (naming every diverging field and both
  sets of values); it then proceeds using the verified record, not a
  re-read.
- **What the anchor doesn't solve.** A registration made before the anchor
  existed stays unverifiable until a single elevated
  `iamtunnel server install` run — the one moment the current profile
  record is trusted (the operator is present and elevated, and the command
  says so in its own output). Once placed, the anchor is never silently
  rewritten: a mismatch at `install` refuses too, since overwriting the
  anchor would bless whatever swapped the record after `enrol`. If the
  anchor itself is destroyed, `server start`'s refusal names both paths: a
  fresh `server install` (same machine) or a fresh `enrol` (registration
  deliberately moved).
- **The Unix side of the same boundary.** Every machine-role command
  requires root (SPEC §3.2.1), and the directory is personal
  (§3.2.2): elevation that preserves the invoking user's `$HOME` (`sudo -E`,
  older sudo configurations, an admin-privileges relaunch that keeps the
  caller's home) would make root act along a chain an unprivileged account
  owns, with the same outcome (a planted `osUser`, the door key landing in
  their `authorized_keys`). The automatic path — a service reading
  `--data-dir /var/lib/iamtunnel-machine`, a root-owned chain — is safe; the
  manual path is guarded by a rule requiring every directory from the data
  directory's parent up to `/` to be root-owned and not group/world-writable
  — whoever can rename an ancestor can carry off everything beneath it. An
  ordinary `sudo` (root's own HOME) and the service directory pass; a
  preserved user HOME refuses, naming two ways out: ordinary `sudo`, or
  `--data-dir` on a root-owned path.

## 4. Invariants and their layers

### 4.1. The core security invariant (§2, item 4)

SPEC states the core invariant verbatim:
> *"After losing an authorized transport, the gateway cannot open a new
> connection to the machine; a forgotten key line on the machine is inert
> (layer 0 + layer 1) and is removed at the first opportunity (layers
> 2–3)."*

This guarantees the target Windows host never stays reachable for
unauthorized entry through any crash, network drop, or control-process
failure. Protection follows defense-in-depth, split into four complementary
layers (§6.3).

---

### 4.2. The four layers in detail (§6.3)

| Layer | What it does and guarantees | Fails to hold when | What backs it up |
|---|---|---|---|
| **Layer 0** *(OpenSSH's own `authorized_keys` restrictions)* | The server writes the door's public key to `administrators_authorized_keys` only after a valid `door.open` request from the gateway over `iamtunnel-control`, an ed25519-key check, local `maxDoorIdle`/`maxDoorHard` ceilings, and **only after the watchdog has already started**. The line carries hard options: `restrict,pty,from="127.0.0.1" iamtunnel-door=<door-id>` — no port forwarding, X11, or agent forwarding; the source address locked to loopback. Written atomically, under a file lock, with the rest of the file preserved byte-for-byte, a read-back and a DACL check. | Doesn't defend against a local user or a compromised Windows service that already reaches `127.0.0.1:22`, if the attacker also holds the door's private key. Doesn't defend against commands run inside the PTY itself. Compatibility limits: Windows 10 1809 / Server 2019's OpenSSH 7.7 rejects the whole line on an unknown option (why `expiry-time` is not used); an sshd build without `restrict` support refuses the line. | **Layer 1**: the door's private key is absent from the machine; even with access to the socket, the attacker cannot complete the handshake without it, and it exists only in gateway RAM. |
| **Layer 1** *(ephemerality of the key in gateway memory)* | The door's private key is generated in gateway RAM only on a confirmed person reservation. It exists only in `opening`, `open`, `closing` for the current epoch's own door, and is never flushed to disk anywhere. In `closed`, it's absent from memory entirely. On tunnel loss or door close, it is forgotten immediately (§5.2). | Compromise of the running gateway process's RAM (memory dump, root, a debugger) while the door is open. Swapping gateway RAM pages to disk on the Linux VPS. Other parallel sessions on the same machine (`sessions > 0`). | **Layers 2 and 3**: with a live server, removal follows timers and transport closure; layer 3 watches the door for its entire life — the watchdog's parent-wait bound is `maxDoorHard` plus a margin (default 8h5m), taken from settings, not a hardcoded number. |
| **Layer 2** *(the server process lifecycle)* | The iamtunnel server on the machine removes the key line under a file lock on: normal Stop (window close, SIGTERM), a confirmed `door.close` from the gateway over `iamtunnel-control` (idle timeout or hard deadline), three missed keepalives in a row (60–90 s), or its own local monotonic `maxDoorIdle`/`maxDoorHard` timer. After confirmed removal, the server stops the watchdog by its saved handle/PID. `SweepStale` unconditionally runs before every Start and reconnect (§3.2). Starting the server does NOT open the door or write the key. | Server process crash (`kill -9`, panic, out of memory). The main thread hanging on blocked I/O. A power failure or OS crash (BSOD). | **Layer 3**: an independent external watchdog process (`doorwatch`) tracking the parent through a kernel handle. |
| **Layer 3** *(the external `doorwatch` process)* | A separate, independent process `iamtunnel server doorwatch <door-id> <parent-pid> <keyfile> <max-wait-ms> <journal-path>`, started **strictly BEFORE the line is written** in the `door.open` handler, outside any job object. Waits for the parent's exit via `WaitForSingleObject`; the parent-wait bound equals `maxDoorHard` plus a margin (default 8h5m), computed from server settings and passed via argv — no hardcoded five-minute number remains. It writes its own cleanup event to a separate journal, whose path also comes via argv, letting a watchdog cleanup be told apart from a server cleanup. On the parent's death, the handle becomes signaled; the watchdog wakes, takes an exclusive lock on `administrators_authorized_keys`, removes the marked line, flushes to disk, and exits. On a normal door close, the server itself removes the line under lock (layer 2) and stops the watchdog by its saved handle/PID (stopping by image name is forbidden). While the door is closed, the watchdog doesn't run; it's on duty for the door's entire open lifetime. | Group process kill (`taskkill /f /im iamtunnel.exe`), killing the server and watchdog together. Instant power loss or a kernel crash (BSOD), stopping all code execution. Disk subsystem hangs. The parent-wait bound (`maxDoorHard` plus margin) expiring: by then the door has already outlived its natural `maxDoorHard` and closed by the server's own monotonic timer. | **Layers 0 and 1**: a line left in the file is inert, since the gateway destroyed the door's private key on the keepalive timeout. At the next server start, `SweepStale` (§3.2) removes the line before a new door opens. |

---

**The single-door-line invariant.** More than one `iamtunnel-door=...` line
is dangerous: an old line might have no live watchdog left, and compromising
its private key would again grant local administrative entry. So a new
`door.open` under the same file lock collapses any line for its OWN
`doorId` (idempotent retry) and writes exactly one new one; it never touches
other lines, including our own corrupted ones — those are removed only by
`door.sanitize` and `SweepStale` (PROTOCOL §5.1, IAMT-94), since sweeping is
outside `door.open`'s own authority. Foreign `authorized_keys` lines are
never touched.

### 4.3. Moving the watchdog's start time

The critical v0.3 change: moving the watchdog's start to **BEFORE** writing
into `administrators_authorized_keys`.

- **The race in the old scheme**: the key line was written first, and only
  then was the watchdog process started. If the server crashed in the gap
  between the disk write finishing and the watchdog's process actually
  existing, the door's public key stayed on disk while no watchdog was armed
  at all — layer 2 failed on the process death, and layer 3 was never
  loaded. The line stayed until the next manual server restart.
- **The new scheme (v0.3/v1)**:
  1. The server gets a `door.open` request over `iamtunnel-control`.
  2. It syntactically validates the Ed25519 key and checks the requested
     deadlines against local `maxDoorIdle`/`maxDoorHard`.
  3. **The server starts the `doorwatch` process**, passing it the server's
     PID and the door id, and gets a handle to the running process. If
     starting the watchdog fails for any OS reason, `door.open` aborts with
     an error, and **the line is never written at all**.
  4. Only after a successful process start does the server lock the file,
     add the key line, read it back, and set the DACL. The current
     interface has no readiness handshake: a successful process start
     doesn't prove the watchdog has already called
     `WaitForSingleObject(parentHandle)`.
  5. *Edge-case analysis*: if the server crashes right after starting the
     watchdog but before touching the file, the watchdog wakes normally on
     the parent handle, locks the file, looks for the `iamtunnel-door=<id>`
     marker, finds nothing, records the absence, and exits cleanly. No side
     effects, no file corruption.
  6. This ordering ("create the process before writing") removes the old
     write-before-create race, though it doesn't give an absolute guarantee
     of observation for the door's whole life. In practice `doorwatch` runs
     with a parent-wait bound equal to `maxDoorHard` plus a margin (default
     8h5m); if the parent somehow outlives that, the watchdog exits with an
     error — but by then the door has already outlived its natural
     lifetime. This defect is closed (IAMT-130).

## 5. Failure-window matrix (§6.3)

Below is a detailed walk-through of every scenario in the v0.3 failure
matrix, with precise vulnerability-window estimates for the two states that
matter: the door **open** (a session was in progress) and the door
**closed** (the machine was connected and idle, default deny).

This walk-through uses the Windows machine
(`administrators_authorized_keys`, `WaitForSingleObject`, `taskkill /f`).
For a Linux machine (v1.1, §3.2.1), the mechanisms and windows are the same
— only the platform details differ (the file
`<osUser-home>/.ssh/authorized_keys`, parent-death detection via `pidfd`,
group kill via `kill`/`systemctl`); the on-call action table for each row is
in RUNBOOK §5.9, and the platform layer specifics are in §3.12 above.

### Scenario 1: network drop between machine and gateway
- **Closing mechanism**: mutual keepalive control (§5.2: 20-second interval,
  3 misses in a row).
- **Trigger latency**: 60–90 seconds from the moment packets stop flowing.
- **Vulnerability window**:
  - *If the door was closed (idle, default deny)*: **0 seconds**. No key
    line in the file, no watchdog running.
  - *If the door was open (a session in progress)*: **60–90 seconds**. The
    open key's public half sits in `administrators_authorized_keys` on the
    Windows host. But the target machine is behind NAT and the tunnel is
    torn down, so inbound access from the Internet is physically
    impossible. On the gateway, the door's private key is erased from
    memory once the keepalive times out; the live server also removes its
    own line under lock once the keepalive timer fires (layer 2). The risk
    of unauthorized entry is zero.

### Scenario 2: normal Stop / window close
- **Closing mechanism**:
  - *Door was open*: the server synchronously removes the key line from
    `administrators_authorized_keys` under a file lock with a confirming
    read-back, stops the watchdog by its saved handle/PID (layer 2), and
    closes the tunnel socket (§3.2). The protected DACL is preserved.
  - *Door was closed*: the server closes the control channel and tunnel
    socket. No file modification, since no key line was ever there.
- **Trigger latency**: immediate and synchronous, before the UI and process
  exit.
- **Vulnerability window**: **0 seconds** with the door closed; **a
  fraction of a second (unmeasured)** with it open (bounded by the
  synchronous locked file-removal operation).
- **Risk analysis**: deterministic, orderly shutdown. No exploitation path.

### Scenario 3: server crash (kill / panic)
- **Closing mechanism**:
  - *If the parent dies at any point from door-open until the parent-wait
    bound (`maxDoorHard` plus margin) expires*: the external `doorwatch`
    process, started **BEFORE** the line was written, waits on the server
    process's handle via `WaitForSingleObject` (§6.3). On the server's
    death, the OS kernel signals the handle; the watchdog wakes, locks the
    file exclusively, removes the door line, flushes to disk, and exits.
  - *If the parent outlives that bound*: by then the door has already
    outlived its own `maxDoorHard` and closed by the server's own monotonic
    timer, so there is nothing left for the watchdog to watch. A residual
    line, if it somehow survives, is removed at the next `SweepStale` and
    is inert without the gateway's half of the key.
  - *If the door was closed*: no line in the file, no watchdog running.
- **Trigger latency**: throughout the door's open lifetime — immediately
  after the parent exits and the kernel call wakes.
- **Vulnerability window**: **0 seconds** with the door closed; **a
  fraction of a second (unmeasured)** throughout the door's open lifetime;
  after its natural end, until the next Start/reconnect running
  `SweepStale`.
- **Risk analysis**: the OS kernel closes the tunnel socket immediately on
  process death (TCP FIN/RST to the gateway). Inbound traffic through the
  tunnel stops instantly, and the watchdog clears the on-disk line — it's on
  duty for the door's whole life.

### Scenario 3b (group kill): forced termination via `taskkill /f /im iamtunnel.exe`
- **Closing mechanism**: `taskkill /f /im iamtunnel.exe` forcibly and
  synchronously kills **every** process by that executable name, so the
  `doorwatch` watchdog dies together with the server. No file cleanup
  happens at that moment. Cleanup runs via `SweepStale` at the next server
  start (§3.2) or before a reconnect. In normal operation, the server stops
  the watchdog strictly by its saved handle/PID, never by image name (SPEC
  §3.2).
- **Trigger latency**: at the next server program start, or on reconnect.
- **Vulnerability window**:
  - *If the door was closed*: **0 seconds**. No line was ever in the file,
    no watchdog was running.
  - *If the door was open*: **from the moment of the kill until the next
    server start (hours to weeks / indefinite)**.
- **Risk analysis**: the public key's line stays in the file, but the tunnel
  is torn down (the machine is unreachable from outside), and the gateway
  destroys the door's private key in RAM after the 60–90-second keepalive
  timeout. The line left on disk is entirely inert. There is no
  compromise risk, thanks to the combination of layers 0 and 1.

### Scenario 4: hardware failure / BSOD / sudden power loss
- **Closing mechanism**: a hardware power interruption stops all code
  execution; cleanup runs via `SweepStale` at the next iamtunnel server
  start (§3.2, §6.3).
- **Trigger latency**: at the next server program start.
- **Vulnerability window**:
  - *If the failure happened while idle (door closed, > 95% of the time)*:
    **0 seconds**. No key line was on disk before the crash, and the file
    stays clean after reboot.
  - *If the failure happened during an active session (door open)*: **from
    the moment of failure until the next server start (tens of seconds to
    days)**.
- **Risk analysis**: the new architecture makes a crash landing inside the
  open-door window far less likely than the old one. If it does happen, the
  key's public half survives on disk, but it's cryptographically inert: the
  gateway's keepalive timeout (60–90 s) erases the paired private half from
  RAM. Authenticating against the leftover line is impossible.

### Scenario 5: gateway crash (gateway OS crash / gateway process killed)
- **Closing mechanism**:
  1. On the gateway: the door's private key is destroyed immediately along
     with the process's address space in RAM (layer 1).
  2. On the machine: the server detects the drop via keepalive (3 misses at
     20 s) or its own monotonic `maxDoorIdle` timer, and removes the key
     line under lock, stopping the watchdog (layer 2).
- **Trigger latency**: on the gateway — 0 seconds; on the target machine —
  60–90 seconds.
- **Vulnerability window**: **0 seconds** with the door closed; **60–90
  seconds** with it open.
- **Risk analysis**: the key line's presence on the machine for up to 90
  seconds is safe: the gateway's half of the key is already erased, and the
  network tunnel is destroyed.

### Scenario 6: full gateway reinstall (VPS reinstall / new host key)
- **Closing mechanism**: the old tunnel drops. Before reconnecting, the
  server on the machine runs `SweepStale` (§3.2), guaranteeing the leftover
  door line is removed. A connection attempt to the new gateway is refused
  outright, since the machine's pinned host-key fingerprint no longer
  matches (§3.1, §6.2).
- **Trigger latency**: the local keepalive fires after 60–90 seconds;
  `SweepStale` runs before the reconnect cycle.
- **Vulnerability window**: **60–90 seconds to clean up the key line (with
  the door open) or 0 seconds (door closed), after which the tunnel is
  permanently blocked until an administrator intervenes**.
- **Risk analysis and design-gap note (see Defect 6, §7)**: the door line is
  guaranteed removed by `SweepStale`. But there's a persistent design gap:
  the target machine pinned the gateway's fingerprint at Set-up step 1 from
  the one-time `enrol` code, and there is no mechanism to remotely update
  that pin on the machine. Machines stay permanently disconnected from the
  gateway until manually reconfigured.

### Scenario 7: two simultaneous sessions, one ends
- **Closing mechanism**: the door stays open; the gateway decrements the
  session counter (`sessions--`) (§5.2, §6.3).
- **Trigger latency**: the door line's removal waits for the last user to
  leave (`sessions == 0 && reservations == 0`) or the hard timeout.
- **Vulnerability window**: **equal to the remaining active session's
  duration (tens of seconds to hours)**.
- **Risk analysis**: the door key stays in the file for the remaining
  operator. If the ended session belonged to a person whose grant was just
  revoked, they cannot open a new connection through the gateway — but the
  remaining session runs under the same `verifiedOsUser` account, which
  carries the cross-session-interference risk noted as Defect 4 in §7.

### Scenario 8 (new in v0.3): all sessions end / door idle timeout
- **Closing mechanism**: once the active session and reservation counts both
  reach zero, the gateway immediately moves the door to `closing` and sends
  `door.close(reason: "idle")` over `iamtunnel-control`; there is no
  separate gateway-side no-I/O timer in the code. The server atomically
  removes the marked line under lock, reads it back, and stops the watchdog
  by its saved handle/PID.
- **Backup mechanism**: if the gateway hangs or fails to send the command,
  the machine's server independently closes the door once its local
  `maxDoorIdle` limit (default 15 minutes) elapses with no tunnel bytes,
  removes the line, and stops the watchdog.
- **Trigger latency**: right after the last session actually ends; if the
  gateway missed it, the server removes the line via its own idle timer
  (15-minute default) only when the tunnel carries no bytes.
- **Vulnerability window**: for the key line, bounded by the local
  idle/hard timer. A hung but connected human session is not closed by this
  timer — it's ended by the gateway's own liveness probe
  (`keepalive@openssh.com`, 20 s × 3, IAMT-126): a silent socket is torn
  down within ≤60 s plus delivery, freeing the `sessions` slot and finishing
  the recording.
- **Risk analysis**: default deny is restored for the key file; any
  gateway/session-socket desync is bounded by the probe's detection window
  (closed by IAMT-126).

| **5. Gateway crash** | Gateway RAM (1) + keepalive (2) | 0 s on the gateway / 60–90 s on the server | **60–90 s** | **0 s** | Inert, cleared on keepalive / no line |
| **6. Gateway reinstall** | `SweepStale` on reconnect | On the reconnect attempt | **60–90 s (then refused)** | **0 s (then refused)** | Removed, tunnel blocked by the pin |
| **7. One of two sessions ends** | The door is held open (§5.2) | `sessions--` decrement | **Duration of the 2nd session** | — | Active for the remaining session |
| **8. All sessions end (idle)** | Gateway (`door.close`) + server | `sessions==0`, 15 min idle | **A normal close (15 min)** | **0 s** | Removed under lock, watchdog stopped |

## 6. What we do NOT defend against (accepted risks)

The following risks are consciously accepted as consequences of design
decisions and platform limits.

### 1. Full compromise of the gateway's operating system (root / `iamtunnel` user)

- **Why accepted**: the gateway is designed as a centralized bastion that
  terminates SSH on both sides in order to make a legally significant
  recording (§1, principle 3). As a result, ephemeral door private keys and
  plaintext interactive sessions exist in the gateway daemon's memory
  during sessions. An attacker gaining root or the `iamtunnel` service
  account on the Linux VPS can directly intercept live sessions and issue
  unauthorized `door.open` requests over `iamtunnel-control`. This tradeoff
  matches the design of comparable bastion architectures.
- **Cost of fully closing it**: giving up gateway-side session termination
  entirely and moving to end-to-end encryption between client and target,
  which rules out centralized video and text recording altogether.

### 2. Protecting the local event journal (`events.jsonl`) and recordings from the gateway's own local admin

- **Why accepted**: `/var/lib/iamtunnel/events.jsonl` and
  `/var/lib/iamtunnel/recordings/` sit on the Linux VPS's local filesystem
  (§3.5). A local superuser (`root`) has absolute power to modify disk
  sectors directly, bypassing append-only logic, deleting files, or
  changing permissions. Software can't defend local files against a
  privileged administrator of the same OS without an external trusted
  system.
- **Cost of fully closing it**: continuous streaming replication of the
  event journal to an independent external SIEM, and immutable, WORM-backed
  network storage for recordings.

### 3. Residual risk of a dead public-key line in `administrators_authorized_keys` after BSOD / power loss

- **Why accepted**: on a Windows kernel crash (BSOD) or sudden power loss,
  process execution halts at the hardware level. The server and its
  watchdog physically can't run their cleanup file operations. OpenSSH's
  `expiry-time` directive is rejected by the spec (§6.3), since target
  machines on Windows 10 1809 / Windows Server 2019 run OpenSSH 7.7, where
  an unknown option breaks the whole authorized-keys file. The risk is
  accepted because, without the gateway's paired private key, the line on
  disk is cryptographically inert (layers 0 and 1), and `SweepStale` removes
  it at the very next program start. **Significant improvement in v0.3**:
  thanks to dynamic door opening, this risk now only materializes during a
  BSOD in the middle of an active session — outside active use (over 95% of
  the time), the door is closed and the file is completely clean.
- **Cost of fully closing it**: writing a custom Windows kernel boot-start
  driver to clean the file before OpenSSH starts, or dropping support for
  Windows 10 1809 and Windows Server 2019 and forcing an OpenSSH 8.7+
  upgrade for the `expiry-time` directive.

### 4. Destructive activity by an operator inside a granted session (post-exploitation)

- **Why accepted**: access is granted to a Windows shell under the local
  administrator account `verifiedOsUser` (§4.3). The OS does not restrict
  an administrator from deleting data, installing drivers, or extracting
  local secrets from LSASS. Defending the target OS against its own
  legitimate administrator is outside the transport protocol's
  responsibility.
- **Cost of fully closing it**: adding granular privilege control (Just
  Enough Administration — JEA), forcibly restricting administrator rights,
  and running sessions inside disposable isolated environments.

### 5. Client's private key stored on the workstation without a passphrase

- **Why accepted**: per §3.1, the client-generated private key is saved to
  `%LOCALAPPDATA%\iamtunnel\key` unencrypted (no passphrase), with access
  restricted to the current Windows user by its own freshly-created ACL —
  the file never lives even a moment with folder-inherited permissions, and
  an existing key's ACL is checked and repaired against the open file handle
  it's read from, not by name. This is done for seamless, non-interactive
  connections without a password prompt at every session. Any malicious
  process running as the same user gets direct access to the private key.
- **Cost of fully closing it**: mandatory strong-passphrase encryption of
  the client key with a prompt at every session start, or hardware-bound
  keys via TPM 2.0 / FIDO2 WebAuthn tokens.

### 6. One string, one field: reading the clipboard or transfer channel during a secret's issuance window

- **Why accepted**: since 1.3, everything carried from machine to machine —
  the gateway's address, its fingerprint, and the secret itself — travels as
  one string (§3.6, design decision, 2026-09-17). Before 1.3, the
  fingerprint and PIN were required to travel over separate channels, which
  assumed an attacker who reads one transfer channel and not the other. Real
  use showed a second channel never materializes — the link and PIN went
  through one message, one screenshot. The rule offered no protection and
  doubled the actions on every connection, so it was removed. **The
  accepted risk is stated plainly: whoever reads the clipboard or transfer
  channel during the two-minute pairing window becomes a gateway
  administrator.** In its place: lifetimes (2 minutes for the pairing PIN,
  15 minutes for a machine invitation, 24 hours for the bootstrap token),
  one-time use (the secret burns in the same atomic `state.json` write as
  its result), a 3-minute address ban after three wrong PINs
  (`E_PAIRING_LOCKED`, IPv6 counted by /64), the window itself burning after
  ten misses across all addresses, a mandatory preview with the gateway's
  fingerprint before the button acts — the one place a human verifies the
  fingerprint, since TOFU is absent from every role (§6.2) — and a "new"
  flag on anything that just joined.
- **Cost of fully closing it**: reverting to two independent channels with
  different carriers (e.g. a link by email, a PIN by voice), which only pays
  off against an attacker controlling exactly one of the two channels, at
  the cost of doubled human actions and, in real-world use, running out the
  two-minute window fighting with the input form. Manual separation remains
  possible — the gateway still prints the link and PIN so they can be
  split — the interface simply no longer forces it.

## 7. Inconsistencies, contradictions, and hidden design gaps

Following in-depth review of the design and protocol documents across
versions, here is the status of every design gap found.

### Gap 1. Door lifecycle dead end and missing control channel — CLOSED in SPEC 0.3 and PROTOCOL.md v1
- **The problem in the earlier draft**: the door used to be opened by the
  server itself at start, via an RPC-style `door.open` call. Once idle
  (`sessions == 0`), the gateway forgot the door key but had no way at all
  to tell the server to reopen the door for a new person — there was no
  channel back from gateway to server. This produced either a dead denial
  of service, or forced keeping the door open around the clock.
- **How it was closed**:
  1. A persistent control SSH channel, `iamtunnel-control` (PROTOCOL
     §§5.1–5.2, SPEC §3.2, §5.2), which the gateway opens to the machine
     immediately after registering the `tunnelEpoch`.
  2. Starting the server (`Start`) no longer calls `door.open` and never
     writes the key (the door is closed by default).
  3. The door is opened only by the gateway, on a confirmed person
     reservation, via `door.open` over `iamtunnel-control`.
  4. The door is closed by the gateway's own `door.close` directive when
     `sessions == 0 && reservations == 0`, or on a hard timeout.
  5. The machine's server got its own independent local deadline ceilings,
     `maxDoorIdle` (15 min) and `maxDoorHard` (8 h), letting it reject
     oversized deadlines from the gateway and forcibly close the door
     regardless of the gateway.
  6. The watchdog starts strictly BEFORE the line is written, and stops by
     PID/handle once close is confirmed.
  7. The PROTOCOL.md §5.2 distributed state machine (`closed`, `opening`,
     `open`, `closing`, a `reconcilePending` flag, and retired-id cleanup)
     fully rules out the old races and dead ends. Fully closed.

### Gap 2. A fictitious `osUser` check at registration step 3 — CLOSED in SPEC 0.3 and PROTOCOL.md v1
- **The problem in the earlier draft**: earlier text claimed step 3's probe
  checked `osUser`'s membership in the Administrators group, but by its own
  description the probe ended at the KEX phase, before any user
  authentication ran. In OpenSSH, group membership and reading
  `administrators_authorized_keys` are both checked strictly during
  per-user authentication — so a machine could register even with a
  nonexistent or unprivileged account named.
- **How it was closed**:
  1. SPEC (§3.4, step 3) and PROTOCOL (§7, the `sshd-probe` phase) now
     describe a real check: after pinning the OpenSSH host key, the gateway
     temporarily opens the door via `door.open` and runs a real SSH
     public-key user-auth attempt as `requestedOsUser`, without opening a
     shell or exec.
  2. Since Windows OpenSSH only consults
     `%ProgramData%\ssh\administrators_authorized_keys` for accounts in the
     Administrators group, a successful auth with the door key
     mathematically proves `requestedOsUser` exists, is active, and holds
     administrator rights.
  3. Only on success does the gateway record `verifiedOsUser:
     requestedOsUser`, `osUserStatus: verified` and `state: verified`. A
     failure leaves the machine `enrolled` with `osUserStatus: rejected`,
     closes the temporary door, and blocks operator access. Fully closed.

### Gap 3. Audit blind spot: lost stdin for `exec` commands and scripted pipes (PROTOCOL §5.1 vs §6.5) — PARTIALLY CLOSED / RESTRUCTURED in SPEC 0.3 and PROTOCOL.md v1
- **The problem in the earlier draft**: the `.cast` format didn't record
  input events (`"i"`), relying on PTY terminal echo. Running a
  non-interactive command via `exec` without a PTY (e.g. a scripted pipe
  `ssh person:machine@gateway < script.ps1`) has no echo, so the stdin
  payload was completely lost to audit.
- **Current status in v0.3/v1**:
  1. SPEC (§5.1, §6.5) and PROTOCOL (§8) introduce a dedicated lossless
     `.exec.jsonl` format for exec without a PTY.
  2. The first entry in this journal atomically records the executed
     command string, then every stdout/stderr chunk, exit-status/
     exit-signal, and EOF, with a mandatory `fsync` before bytes reach the
     human.
  3. *Remaining aspect*: if an attacker feeds a large script or command
     stream over standard input in the `session` channel (RFC 4254 §5.2),
     `.exec.jsonl` still records the fact of the command's execution and
     all output it produced, but the incoming stdin stream itself still has
     no dedicated record type (unlike stdout/stderr). Since 1.46 (R4 F-03):
     under a shell grant, stdin is still carried and remains outside the
     recording — the gap stands there. On a grant with the `exec`
     capability, the gap is closed outright: the gateway closes the
     machine's stdin right after forwarding the command and refuses any
     bytes the human still writes (`E_SSH_STDIN_FORBIDDEN`, PROTOCOL §4.1) —
     there's nothing to carry, so nothing to audit; the text classifier
     additionally flags interpreters that read stdin as yellow
     (`stdin-interpreter`, PROTOCOL §6.1), but this is a hint, not an
     enforcement.

### Gap 4. No isolation between different people's sessions under one shared `osUser` account (§4.3, §5.2, §6.3, §6.4) — REMAINS (an accepted 1.0 limitation)
- **The problem**: multiple operators can work simultaneously on the same
  machine through one open door under the shared `verifiedOsUser` (a local
  Administrator) account.
- **Vulnerability and consequences**: since parallel sessions run under the
  same fully-privileged Windows user, OS-level security offers no isolation
  between operators' processes: a bad-faith operator could use standard
  Win32 APIs to inject into a parallel session's processes, capture input,
  or swap running code. Revoking a bad-faith user's access only closes the
  network channel — any background process they already started under
  `verifiedOsUser` keeps running unimpeded.
- **Status**: SPEC §12 reaffirms the 1.0 architectural decision: "The door
  key is one per door, with a session counter." The risk is acknowledged and
  listed among the accepted risks.

### Gap 5. No standard recovery mechanism when the last admin key is compromised or lost (§3.3 vs §3.5 vs §7.2) — REMAINS
- **The problem**: if the sole admin key is lost or compromised, no subject
  remains able to run `admin` commands (§5.3). A repeated `gateway install`
  per §3.5 is idempotent: it "never touches `state.json` or `hostkey`" and
  issues no new bootstrap token; there's no console subcommand to add an
  admin key directly (e.g. `gateway add-admin-key`) in §7.2.
- **Vulnerability and consequences**: the system's administrative control
  loop locks up entirely. The only recovery path used to be risky manual
  editing of `state.json` on a stopped service, or a full gateway redeploy
  from a trusted backup (`gateway restore <backup>`).
- **Actual status as of 2026-09-17**: a standard local path now exists —
  `gateway pair` on a stopped gateway (`stop` → `gateway pair` → `start`,
  RUNBOOK §5.11) — and manual `state.json` editing is no longer needed.
  Separately: for the **first** admin, this emergency path was never needed
  at all — since 1.3, `gateway install` prints a ready paste-in string, and
  `gateway status` reprints it while it's still good (§3.3). It was
  precisely the absence of that second fact that drove a real-world drill
  into the emergency path: the bootstrap token silently expired in a day
  with nowhere to look at it again. The problem description above is kept
  as history; this paragraph is the current status.

### Gap 6. No way to remotely re-pin the gateway's host key on registered machines after a gateway reinstall (§3.4 vs §6.2) — REMAINS
- **The problem**: at Set-up step 1 (§3.4), the target machine's server
  hard-pins the gateway's fingerprint from the one-time registration code
  `iamtunnel-enrol://...#<sha256 host key>:<secret>`. On an unplanned
  catastrophic gateway reinstall (loss of the VPS host key), a new gateway
  host key is created. Per §6.2, `gateway rotate-hostkey` only generates
  new connection strings for human clients, assuming a transition period.
  `machines rekey` updates a machine's own sshd fingerprint, not the
  gateway's. There's no mechanism to remotely update a machine's pinned
  gateway fingerprint.
- **Vulnerability and consequences**: on an emergency gateway key loss,
  every registered machine in the fleet detects a fingerprint mismatch
  (`the gateway host-key fingerprint changed`) and refuses to connect
  permanently. Each target machine needs a manual visit and a fresh
  registration from scratch.

## 8. Low-cost hardening opportunities

Below is an updated list of low-cost security improvements, with their
implementation status in the v0.3/v1 architecture:

1. **Forced recording of the STDIN stream for `exec` sessions and scripted
   pipes**
   - *Status in v0.3*: done for the required outward audit —
     `.exec.jsonl` records the command, every lossless stdout/stderr chunk,
     exit-status/exit-signal and EOF with a mandatory `fsync` before
     reaching the human. Incoming STDIN chunks deliberately have no
     dedicated record type (§6.5). Since 1.46 (R4 F-03), an exec-capability
     grant carries no stdin at all (closed by the gateway,
     `E_SSH_STDIN_FORBIDDEN`) — recording is only needed under a shell
     grant, where the gap stands.
2. **A control RPC channel from gateway to machine (`iamtunnel-control`)**
   - *Status in v0.3*: **FULLY DONE** in SPEC.md v0.3 and PROTOCOL.md v1
     (§5.1, §5.2). A persistent `iamtunnel-control` channel carries
     `door.open`, `door.close`, `door.status`. The door opens dynamically
     only under a user's session, closing the dead end of Gap 1.
3. **Real verification of the `osUser` account at Set-up and user changes**
   - *Status in v0.3*: **FULLY DONE** in SPEC.md v0.3 (§3.4, step 3) and
     PROTOCOL.md v1 (§7). The gateway runs a real SSH public-key probe of
     `requestedOsUser` through a temporary open door with no shell, strictly
     confirming Administrators membership before `verified` status is set.
4. **A per-session unique door key (session-isolated door keys)**
   - *Mechanism*: a personal door key per incoming person
     (`iamtunnel-door=<door-id>-<session-id>`). On that person's exit, only
     their own line is removed, leaving parallel sessions untouched.
   - *Note*: would require revisiting the owner's SPEC §12 decision ("The
     door key is one per door, with a session counter"). Proposed as a
     future change request for session isolation (Gap 4).
   - *Estimated effort*: roughly 90 lines across `internal/gateway` and
     `internal/winkeys`; about 1.5 person-days.
5. **Cryptographic hash-chaining of the event journal (`events.jsonl`)**
   - *Mechanism*: each journal line carries `prev_hash: SHA256(...)` of the
     previous line, making silent tampering, deletion, or backdated forgery
     technically detectable.
   - *Estimated effort*: roughly 60 lines in
     `internal/gateway/events`; about 1 person-day.
   - *Status*: **DONE** (1.14, IAMT-467) — this is exactly the chain
     described in PROTOCOL §1.7, checked by `iamtunnel gateway
     verify-journal` and the Gateway tab.
6. **Sanitizing the key file at OS start via Windows Task Scheduler**
   - *Mechanism*: register a scheduled task `iamtunnel server clean` on
     "At startup", running `SweepStale`. This meaningfully shrinks the
     BSOD vulnerability window (from indefinite to tens of seconds after
     boot). It can't eliminate the window entirely, since the Service
     Control Manager starts `sshd` in parallel and it begins listening
     before the scheduled task runs.
   - *Estimated effort*: roughly 70 lines in `internal/server`; about 1
     person-day.
7. **Zeroing ephemeral private keys explicitly in memory**
   - *Mechanism*: explicitly zero the Ed25519 private-key byte slices in the
     gateway right after a door closes or a tunnel drops, instead of
     leaving them on the Go heap until garbage collection.
   - *Estimated effort*: roughly 30 lines in `internal/gateway`; about 0.5
     person-days.
8. **Unbounded watchdog observation of an open door**
   - *Status*: **CLOSED** (IAMT-130). The watchdog gets a
     `maxDoorHard`-plus-margin bound (default 8h5m) through argv, sourced
     from server settings, no hardcoded value in the code.
   - *What remains*: the watchdog exiting on that bound only reaches the
     child process's own error stream, not a dedicated journal event. By
     the time the bound is reached, the door is already closed by its own
     monotonic timer, so this doesn't reopen the window in practice, but the
     journal's silence here is tracked as a separate follow-up.
9. **Liveness for the human SSH session**
   - *Status*: **CLOSED** (IAMT-126). The gateway also probes the human end
     of a session: an SSH-level global request `keepalive@openssh.com`
     every 20 s, a miss on no reply/failure within the interval, three
     misses in a row meaning death (numbers and mechanism symmetric with
     the machine side, PROTOCOL §4.2). A silent transport is closed, the
     bridge ends on a read error, the recording is finalized as
     interrupted, and the session slot is freed — a hung "live" session no
     longer holds a door or a recording open indefinitely.
10. **Journal flooding by unauthenticated traffic, and archive retention**
    - *Status*: **CLOSED** (R4 F-11, 24.09.2026; together with IAMT-452).
      The gateway's port sits on the Internet, and before this fix every
      TCP connection with no key wrote `auth.handshake_failure`, and every
      offered key wrote `auth.failure` — one line, one lock, one fsync per
      attempt, regardless of what the limiter decided. Rotation (IAMT-452)
      moved the growth into archives, but nothing pruned the archives — a
      flood-filled disk stayed flood-filled, and a full journal refuses
      writes for everyone (`E_AUDIT_UNAVAILABLE`, IAMT-451). Now failures
      are folded like successes are (PROTOCOL §1.7: one line per (host,
      cause class) per quiet period, a summary count at the end; slow
      brute force still gets a line per attempt), and the gateway itself
      prunes rotation archives: age (`JournalArchiveRetentionDays`, 30
      days) and count (`JournalArchiveMaxCount`, 20, newest surviving),
      each deletion an `admin.op journal.archive.prune`.
    - *What remains*: (a) there's no limit on the number of SIMULTANEOUS
      unauthenticated handshakes from one address — the accept goroutine
      still spawns before a ban applies; a journal line no longer amplifies
      this, but memory and file descriptors still do. (b) Tagged restore
      names (`ArchiveNameFor`) aren't recognized as prunable by their shape
      — the gateway only removes what it created by rotation; an operator
      removes those by hand.

## 9. Architecture-change analysis for version 0.3: better and worse

Moving in SPEC 0.3 / Protocol v1 to dynamic door control over a persistent
`iamtunnel-control` channel is a fundamental security-architecture change.
Below is an honest, uncompromising account of what this reform closed, and
what new attack surface and dependency it introduced in exchange.

### 9.1. What the new scheme does BETTER (closed threats and shrunk windows)

1. **Default-deny closed door**:
   - *Before*: the server opened the door on pressing Start and kept the
     gateway's public key in
     `%ProgramData%\ssh\administrators_authorized_keys` continuously, 24/7,
     as long as the tunnel to the gateway stayed alive. Even weeks without
     any engineer connecting, the authorization key physically sat in a
     system file on Windows.
   - *Now*: starting the server never opens the door or touches the
     authorization file. The door only opens on an authorized person's
     confirmed reservation. Over 95% of the time on typical servers, the
     authorization file is entirely free of iamtunnel keys, so a local
     malicious process or compromised service on the host cannot use the
     door line — it's physically absent from disk.
2. **Radically reduced probability and window of the BSOD residual risk**:
   - *Before*: with the key present on disk constantly, any power failure or
     Windows kernel crash (BSOD) guaranteed a dead key line in the
     authorization file until the next manual server restart.
   - *Now*: since the door is only open during an active session, the
     chance of a power failure or BSOD coinciding with an open door dropped
     by orders of magnitude. On the overwhelming majority of reboots or
     power failures, the authorization file stays clean, and the risk
     window is zero.
3. **Closing the watchdog-start race (watchdog before write)**:
   - *Before*: the watchdog started after writing the key file. A server
     crash between the disk write and starting the watchdog left the key
     line on disk unguarded.
   - *Now*: the watchdog is created strictly BEFORE the file is modified.
     If starting it fails, writing the line is blocked entirely. This
     removes the old write-before-create race. The production watchdog no
     longer has a hardcoded five-minute limit — the parent-wait bound comes
     from settings (`maxDoorHard` plus margin).
4. **Resolving the lifecycle dead end (Gap 1)**:
   - *Before*: with no feedback channel from gateway to server, reopening
     the door after an idle timeout (`sessions == 0`) was impossible.
   - *Now*: the `iamtunnel-control` channel lets the gateway dynamically
     request a door open for every new connection and close it on idle,
     turning the door into a manageable, temporary barrier.
5. **Introducing local machine sovereignty (`maxDoorIdle`, `maxDoorHard`)**:
   - *Before*: the machine blindly depended on the gateway's own decision
     about when to close a session.
   - *Now*: the machine's server enforces its own independent time
     ceilings (`maxDoorIdle` default 15 minutes, `maxDoorHard` default 8
     hours). The server rejects gateway requests exceeding local limits and
     closes the door on its own monotonic timer, independent of the
     gateway's state or good faith.
6. **Removing the fictitious administrative-rights check (Gap 2)**:
   - *Before*: registration step 3 finished without actually checking user
     rights.
   - *Now*: a full SSH public-key probe through a temporary door proves
     `requestedOsUser` genuinely belongs to the local `Administrators`
     group, ruling out registration with a non-working account.
7. **No standing background watchdog process**:
   - With the door closed, `doorwatch` consumes no resources and holds no
     handles. It's created for an open door and stops cleanly by saved
     PID/handle once it closes; the old premature five-minute exit is gone
     — its lifetime now covers the door's whole life.

---

### 9.2. What the new scheme does WORSE (new attack vectors and stronger dependencies)

1. **The persistent `iamtunnel-control` channel — a new critical attack
   surface on the target Windows machine**:
   - *Before*: the machine↔gateway connection in the earlier design was
     purely a passive transport. The server accepted `iamtunnel-target`
     channel-opens and transparently spliced them into the local
     `127.0.0.1:22` socket, with no application-layer parsing by iamtunnel
     code. The privileged Windows server never parsed incoming application
     protocols from the network.
   - *Now*: the iamtunnel server process, running with elevated Windows
     privileges (local administrator / elevated UAC / SYSTEM), keeps an
     `iamtunnel-control` channel continuously open, constantly reading
     network packets, parsing JSON strings up to 16 KiB, fields, UUIDs, and
     dispatching calls.
   - *Threat*: any vulnerability in the JSON parser, struct deserialization,
     buffer handling, or state-machine logic inside `internal/proto` and
     `internal/server` can now be remotely exploited over the control
     channel — from the gateway itself, or from an attacker who has hijacked
     control of it — to run code in a privileged Windows context.
2. **Materially stronger dependency on the gateway, if it's compromised
   (rogue door open)**:
   - *Before*: the old scheme gave the gateway no way to force the machine
     to open a door unless the server itself called `door.open` at its own
     start.
   - *Now*: the gateway can **initiate opening a door at any arbitrary
     moment** on any connected machine.
   - *Threat*: if an attacker takes control of the Linux VPS's OS
     (compromising the `iamtunnel` or root account), they can mint an
     arbitrary Ed25519 key pair and send a `door.open` directive over
     `iamtunnel-control` to any connected online machine — even with no
     legitimate user requesting access and no grant in `state.json` at all.
     The machine's server only checks the key's syntax and the deadlines
     (≤ 15 min idle, ≤ 8 h hard), starts the watchdog, and obediently writes
     the attacker's key to `administrators_authorized_keys`. The
     compromised gateway then opens `iamtunnel-target` and gets in as a
     full Windows administrator. The machine's server has no way to
     independently double-check that a real person or grant exists behind
     it — it unconditionally follows the gateway's directive.
3. **A more complex distributed state machine, and desync risks**:
   - Adding the asynchronous control channel required a four-phase door
     automaton (`closed`, `opening`, `open`, `closing`), `sessions` and
     `reservations` counters, a `reconcilePending` flag, background
     `door.status` reconciliation queues, and retired-id cleanup.
   - New failure and race classes appeared: control-directive timeouts
     (`E_CONTROL_TIMEOUT`: 10 s on open, 5 s on close), door-marker
     conflicts (`E_CONTROL_DOOR_CONFLICT`), tunnel-epoch desync
     (`E_CONTROL_EPOCH_STALE`).
   - Under network lag, the gateway might record a `door.open` timeout and
     refuse the person, while the machine, delayed, still opens the door.
     Code must follow the late-reply cleanup path (closing a known late
     door, or running `door.sanitize` for a corrupted marker) and the
     background `door.status` reconciliation; there is no separate wire
     operation for late-reply cleanup.
4. **Denial of service via control-channel duplication**:
   - Per PROTOCOL §5.1's normative rule, the machine refuses a second
     `iamtunnel-control` channel-open with `E_CONTROL_CHANNEL_DUPLICATE`.
     But on getting that duplicate refusal, the gateway treats the whole
     `tunnelEpoch` as unusable, **forcibly closing the entire SSH
     transport** and dropping every active session to the machine.
   - This is a denial-of-service path if the gateway itself (through a bug
     or compromise) tries to open a second control channel: handling the
     refusal tears down transport and sessions. An external on-path attacker
     can't simply inject such an SSH packet without breaking the SSH
     transport's integrity; the risk belongs to the code or to trusting the
     gateway, not to a passive network position.
5. **Two time sources — a risk the current code avoids**:
   - Deadlines are indeed handed over by the gateway in UTC, but the server
     only checks their relative order and the `idle-opened`/`hard-opened`
     differences, running its own timers as durations from the local
     moment of receipt. So ordinary clock drift between the VPS and the
     Windows host does not by itself cause a `door.open` refusal in this
     implementation — claiming otherwise would be inaccurate. What remains
     is the risk of a mistakenly formed or oversized duration from the
     gateway, which is still bounded by the machine's own
     `maxDoorIdle`/`maxDoorHard`.

## IAMT-402 / IAMT-403 threat notes

Goal is operator context, not an authorization boundary. It is stored per
person/machine pair, not per connection, and is included with every exec
classification from that pair. `goal.set`/`goal.current`/`goal.history` take
that person explicitly, naming the grant holder the goal is declared for; an
admin declaring a goal for someone else's grant does not file it under the
admin's own identity, and it does not silently vanish from that other
person's session. Both command and goal pass the same scrubber before
external transport and journal output. The bounded newest-first history is
capped at 20; clearing current does not silently promote an old goal.
`rules` ignores goal content for the verdict and exposes `goalApplied:false`
so context cannot masquerade as enforcement.

The write-only `risk.key` operation reduces accidental secret disclosure: a
candidate is probed once before atomic replacement, the previous key remains
active on failure, and live classifier snapshots keep existing
classifications on their original client. State/status contain only
presence and a fingerprint; replacement audit entries contain actor/time and
fingerprints, never key material. In `ai`, loss of the external classifier
is fail-closed and produces `E_RISK_CLASSIFIER_UNAVAILABLE`; an operator
must explicitly select `rules`/`both` or use the live `risk mode log`/`warn`
escape.
